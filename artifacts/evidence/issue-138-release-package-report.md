### Причина выбора исправления

До изменения транспорта свежий `/help` отправлен **01:52:43 UTC**, ответ прочитан в Telegram с датой **02:00:51 UTC**: разница **488 секунд**. Polling обошёл входящую задержку, но следующий контроль выявил отдельный исходящий timeout: обработчик завершился через **30044 ms**, `uncertain`, attempts=1, без receipt. Повтор этой отправки не выполнялся. Проверки TCP/проверяемого TLS и разных режимов соединений подтвердили, что часть новых TCP-соединений не устанавливается; повторное использование соединения само по себе не объясняет сбой.

Применены два изменения:

- `ops/telegram-poller.mjs` и отдельный Compose project принимают `getUpdates` через существующий исходящий proxy и передают события прежнему защищённому обработчику. Offset подтверждает только обработанную пачку; при перезапуске неподтверждённые события проходят прежнюю DB-дедупликацию. `drop_pending_updates=false`; `allowed_updates` сохранены, старый бот не включался. Текущий webhook URL намеренно пуст.
- Общий `ops/telegram-transport.mjs` использует установленный Undici `RetryAgent` **только внутри CONNECT**, с таймаутом заголовков 1500 ms и максимум восемью повторами. Запросы Bot API не оборачиваются в retry. Проверка потерянного ответа после принятого POST подтверждает отсутствие повторной отправки POST. TLS verification остаётся включённой. Предварительный live-прогон этого подхода: **12/12 getMe**, включая соединения после зависшего CONNECT.

### Конкретный незакрытый технический риск

`getMe` старого бота из app-контейнера через настроенный `TELEGRAM_API_PROXY` завершился `TimeoutError`. После уточнения диагностики повторный вызов снова завершился timeout на `getMe`. TCP-соединение к самому настроенному HTTP proxy устанавливается, но отдельный GET `https://api.telegram.org/` через этот proxy также завершился `TimeoutError` за заданные 15 секунд. Причина внутри proxy/upstream/маршрута пока не установлена; TCP connect не доказывает успешный CONNECT или Telegram TLS.

Тот же старый bot credential успешно выполнил три разрешённых read-only Bot API вызова из локальной сети. Для этого token прочитан из runtime только в память локального процесса через SSH, без вывода и сохранения в evidence/argv. Настроенный production proxy не отключался и не обходился в runtime. Это подтверждает рабочий credential и различие сетевых путей, но не исправляет исходящую доставку приложения.

До переключения нужно восстановить или подтвердить работоспособность именно используемого приложением исходящего пути. Замена bot token сама по себе не подтверждает это условие. Ответ поддержки провайдера не требуется как обязательный шаг; диагноз не назначает виновника. Разрешения на исправление proxy, перезапуск и deploy этот read-only этап не даёт.
