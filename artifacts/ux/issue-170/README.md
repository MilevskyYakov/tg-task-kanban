# Таска — реализация принятого лендинга (#170)

## Решение и границы

Владелец принял локальный макет и разрешил реализацию: «очень понравился черновик, давай делать». Дословные тексты и границы сохранены в `approved-copy.md` и опубликованы с обратной проверкой: https://github.com/MilevskyYakov/tg-task-kanban/issues/170#issuecomment-5968294780.

Основа реализации — `index.html` / `review.html`, сохранённые как просмотренный первоначальный макет. Рабочая версия находится в `apps/web/src/landing.tsx` и `landing.css`. Сохранены светлая зелёная палитра, логотип, локальный Manrope, самостоятельные композиции трёх сценариев и мобильная раскладка. После обратной связи владельца телефон заменён на CSS-макет серебристого iPhone 17 Pro Max с Dynamic Island, тонкой рамкой, боковыми кнопками и индикатором Home. Появление телефона и фрагментов реализовано конечными CSS-анимациями; режим уменьшенного движения отключает их. Интерактивное демоприложение и полноценный переход из переписки в канбан не реализовывались.

Все изображения рабочего лендинга пересняты с настоящего Mini App на нейтральных синтетических данных: «Проект», «Поездка», «Ремонт», «Личное». Primex, VPN и другие названия компаний из примеров удалены; согласованная подпись автора «Создано kAIros» сохранена. Вместо смещённого целого скриншота плашки используют снимок полного DOM-элемента задачи с естественными пропорциями. Под «Начать просто» добавлена декоративная композиция сообщения, задачи и отметки выполнения, включая мобильный вариант.

Воспроизведение изображений: запустить Vite на `127.0.0.1:4181`, затем `node artifacts/ux/issue-170/render-assets.mjs`. Скрипт запускает изолированный Chromium, перехватывает API и Telegram, фиксирует дату и использует реальные компоненты без изменения их стилей. Результаты — `apps/web/public/brand/landing-*.png`; данные и границы карточек — `asset-capture.json`. Исторический `app-preview.webp` и принятый первоначальный HTML-черновик не менялись. Ориентир корпуса: [Apple iPhone 17 Pro Max — Tech Specs](https://support.apple.com/en-us/125091), вид спереди; это иллюстрация устройства, не фотография и не проверка на физическом iPhone.

Существующий вход сохранён: адрес приходит из `/api/bot-entry`, проверяется по разрешённому шаблону `https://t.me/<username>?start=landing`, при ошибке доступен повтор. Остались инструкция «Telegram не открылся?», offline-состояние и keyboard skip link. Все три CTA открывают один настроенный адрес. CSS лендинга не меняет стили Mini App.

Продуктовые изменения ограничены публичным лендингом. Бот, API/MCP, экран Mini App, адреса и секреты не меняются. Новых npm-зависимостей и изменений lockfile нет. После локальной приёмки владелец отдельно разрешил commit, PR, merge и deploy; текущий результат выпуска фиксируется в `verification.md` и PR #172. В предрелизных браузерных тестах исправлен порядок очистки: страницы закрываются до тестового API, как в соседних проверках.

## Локальный просмотр рабочей сборки

Адрес запущенного просмотра: http://127.0.0.1:4182/.

`serve-preview.mjs` использует настоящий `buildApp` и собранный web/dist, без запуска планировщиков и Telegram polling. Секреты случайные, токен бота синтетический, сервер слушает только loopback, изменения через API/MCP заблокированы. `/api/bot-entry` выдаёт адрес бота `kairostask_bot`, настроенный явно для просмотра. Нажатие CTA пользователем открывает Telegram; автоматическая проверка перехватывала этот переход до внешнего запроса.

Для повторного запуска после сборки:

```sh
npm run build
TEST_DATABASE_URL='postgresql://milevsky.yakov@127.0.0.1:5432/tasca_issue170_local_checks' node artifacts/ux/issue-170/serve-preview.mjs
```

База `tasca_issue170_local_checks` создана отдельно на локальном PostgreSQL; применены миграции репозитория. Не использовать production-базу. Сервер дополнительно отвергает другое имя базы и нелокальный host.

## Проверочный путь

Пакеты из существующего lockfile установлены через `npm ci --include=dev --ignore-scripts`. Явный `--include=dev` понадобился для Playwright. Установленный Chromium использован с новым изолированным контекстом, без личного браузерного профиля и платного backend.

До изменений показательный сценарий `landing.spec.ts --grep 1440x1000` прошёл на исходном лендинге. После переноса добавлены проверки точного текста из `approved-copy.md`, трёх CTA, skip link, адаптивов 320/390/768/1024/1440/1920, удвоенного текста, ошибки API и недоверенного адреса, font/blur fallback, промежуточного и конечного состояния анимаций.

Первый расширенный прогон обнаружил, что старое поле `use.reducedMotion` в Playwright не применялось. Исправлено общее место: `use.contextOptions.reducedMotion`. Тест теперь проверяет и сам media query, и отсутствие анимации. Режим с движением проверяется отдельно через `page.emulateMedia`.

Команды итоговых проверок и результаты см. в `verification.md`. Сырые журналы, JSON и PNG находятся в `artifacts/visual-evidence/issue-170/` (Git-ignored). `built-*.png` относятся к настоящей локальной production-сборке; `landing-*.png` — к браузерному harness с синтетической настройкой входа.

## Граница выпуска

Локальная проверка не заменяет физические Telegram iOS/Android и production smoke. Принятый текст использует существующее приглашение на доску по ссылке (`pair-board.tsx`); браузерный/API/DB-путь покрывает `pair.spec.ts`. Карточка Таски `92280f50-d94a-48c8-af25-547ddf2154e8` относится к отдельному удобному сообщению для пересылки: её прочитанное описание явно исключает блокировку лендинга. Реальная пересылка сообщения на физических Telegram-клиентах не проверялась и не объявляется выполненной. Карточка и бот не изменяются в этом выпуске.

`npm audit` сообщает одну существующую moderate-уязвимость Fastify: GHSA-4mh8-r7rc-xpvc (HTTP/2 trailer responses, исправление с 5.12.5). Зависимости в этой задаче не обновлялись; это не результат изменения лендинга.
