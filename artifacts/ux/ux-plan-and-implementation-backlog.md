# TG Task Kanban — согласованный UX-план и implementation backlog

Дата фиксации: 2026-08-14  
Статус: визуальное направление и основные продуктовые экраны одобрены  
Канонический макет: `artifacts/ux/task-list-visual-directions.pen`

## 1. Зафиксированное направление

### Продуктовая модель

- Обычный запуск открывает основной экран незавершённых задач.
- Запуск из Telegram-чата открывает связанную чат-доску, но не перезаписывает глобально выбранную доску.
- Главная сущность интерфейса — задача. Доски задают контекст, проекты организуют задачи.
- Нижняя навигация: **Задачи / центральный `+` / Настройки**.
- Один экран решает одно основное действие.
- Полезные режимы не удаляются из-за неудачной текущей подачи.

### Визуальная система

- Направление: **Refined Editorial**.
- Светлые нейтральные поверхности, выразительная editorial-типографика, синий primary.
- Коралловый используется для срочности и ошибок, не как общий декоративный цвет.
- Секции сроков имеют отдельные цветные поверхности, иконки и локальные акценты.
- Строки задач лёгкие; экран не превращается в стопку тяжёлых карточек.
- Небольшие функциональные faux-3D glyph используются точечно: заголовок, колонка, раздел настроек.
- Цвет не является единственным носителем значения: сохраняются подписи, иконки и форма состояния.
- Тёмная тема должна учитывать Telegram theme params, но не входит в первый UI-инкремент.

## 3. Информационная архитектура

### Задачи

Состояния экрана:

1. **Список → По срокам** — состояние по умолчанию.
2. **Список → По проектам** — тот же набор задач, другая группировка.
3. **Канбан → По статусу** — одна полноширинная мобильная колонка.

Общие элементы:

- заголовок `Задачи`;
- выбранная доска справа от заголовка;
- поиск;
- фильтры и число активных условий;
- переключатель списка/канбана;
- сохранение выбранного режима, фильтров и позиции списка;
- завершённые скрыты по умолчанию и доступны отдельным фильтром.

### Выбор доски

Кнопка в заголовке открывает нижнюю шторку:

- `Все доски`;
- недавние доски;
- поиск;
- переход к управлению досками.

Правила:

- последний глобальный выбор запоминается;
- запуск из Telegram-чата временно открывает связанную доску;
- возврат из чат-контекста восстанавливает предыдущий глобальный выбор.

### Список по срокам

Порядок групп:

1. Просрочено.
2. Сегодня.
3. Ближайшие.
4. Без срока.

Каждая группа — самостоятельный визуальный контейнер. Внутри строки плотнее, между группами больше воздуха.

Строка задачи содержит только:

- completion control;
- название;
- проект;
- срок;
- исполнитель;
- срочность;
- блокер;
- компактный прогресс чек-листа при наличии.

Описание, обсуждение, вложения и история открываются только внутри задачи.

### Список по проектам

- Использует тот же компонент строки задачи.
- Группы строятся по активному проекту; `Без проекта` идёт последней.
- В строке вместо повторения проекта можно усилить срок.
- Два списка одновременно не показываются.

### Канбан

- Статусы: **Новая / В работе / Блокер / Готово**.
- На мобильном видна одна полноширинная колонка.
- Статусы переключаются вкладками и горизонтальным свайпом.
- Четыре узкие колонки и drag-and-drop между ними не используются.
- Изменение статуса выполняется явным действием; результат оптимистичный с rollback при ошибке.

### Создание задачи

Центральный `+` сразу открывает полноэкранное создание.

Основные поля:

1. Название — обязательно.
2. Доска — автоматически из текущего контекста; в глобальном контексте обязательна.
3. Проект.
4. Исполнитель.
5. Срок.

`Дополнительно` содержит описание, приоритет, уведомление исполнителя, повторение и другие редкие поля. После успешного создания возврат происходит в исходный контекст; новая задача видна без полной перезагрузки.

### Детали задачи

Разделы:

1. **Главное** — статус, проект, исполнитель, срок, приоритет.
2. **Содержание** — описание и чек-лист.
3. **Обсуждение** — комментарии и вложения.

История, архив, удаление, повторение и другие редкие действия находятся в `•••`.

При возврате восстанавливаются:

- выбранная доска;
- режим списка/канбана;
- группировка;
- фильтры;
- позиция прокрутки;
- активная колонка канбана.

### Настройки

Корневой экран содержит только три входа:

1. **Рабочее пространство** — доски, проекты, участники.
2. **Автоматизация** — повторения, публикации, уведомления.
3. **Аккаунт** — профиль и личные параметры.

Существующие функции сохраняются, но переносятся на дочерние экраны. Корневой экран не становится длинной страницей toggles и технических значений.

## 4. Блокеры

Пользовательский статус называется **Блокер**; внутреннее значение `waiting` можно сохранить для обратной совместимости.

Виды блокера:

1. Другая задача.
2. Внешний фактор с обязательным текстовым объяснением.

Правила:

- причина обязательна;
- дата проверки необязательна;
- внешний блокер снимается вручную;
- после завершения задачи-блокера зависимая задача автоматически переходит в `Новая`;
- исполнитель зависимой задачи получает уведомление;
- циклические зависимости запрещены;
- архивирование или удаление задачи-блокера не должно молча разблокировать зависимые задачи.

## 5. Текущее состояние кода и разрывы

Evidence:

- `apps/web/src/main.tsx` — монолитный React-компонент около 32 KB, смешивает auth, загрузку, навигацию, формы, drag-and-drop и все продуктовые поверхности.
- Начальное состояние `view = 'boards'`; обычный запуск сейчас ведёт к доскам, а не к задачам.
- Создание постоянно встроено в экран доски.
- Редактирование, блокировка, проекты, повторы, комментарии и вложения используют `window.prompt`/`confirm`.
- Текущий канбан рендерит четыре колонки и поддерживает desktop/touch drag-and-drop.
- Текущий текст статуса: `Жду`; согласованный: `Блокер`.
- `apps/web/src/style.css` — прежний тёмный прототип, не соответствует Refined Editorial.
- Фильтрация уже выделена в `apps/web/src/tasks.ts`; её можно расширить без новой state-management зависимости.
- Backend уже поддерживает доски, проекты, участников, задачи, фильтры, чек-листы, комментарии, вложения, историю, повторы и публикации.
- DB поддерживает только текстовый `wait_reason` и `wait_check_at`; структурированной зависимости задача-задача нет.
- Telegram publications всё ещё используют подпись `Жду`.
- `startapp=task_<board>_<task>` генерируется публикациями, но текущий web startup трактует любой `start_param` как board-link token. Deep link задачи требует отдельного маршрута.
- В web нет router или icon dependency. Первый инкремент не требует их добавления: достаточно небольших компонентов, URL/history API и локальных SVG.

## 6. Implementation backlog

Порядок учитывает зависимости. Каждый пункт должен быть отдельным agent-ready Issue/PR.

### P0. Защитить существующее поведение перед UI-разбором

**Цель:** сохранить auth, board context, CRUD и collaboration при декомпозиции монолита.

Scope:

- добавить тесты для стартового контекста: обычный запуск, board-link, task deep link;
- добавить unit tests группировки по срокам и проектам;
- добавить unit tests восстановления view state;
- зафиксировать status/priority display mapping;
- не менять внешний UI.

Acceptance:

- новые тесты падают при возврате стартового экрана к доскам;
- тесты покрывают timezone boundary для `Сегодня`;
- `npm run test:unit`, typecheck и build проходят.

### P1. Разделить web-монолит и добавить app shell

**Цель:** получить минимальную структуру для экранов без новой framework-зависимости.

Scope:

- вынести API client и доменные типы;
- выделить `AppShell`, нижнюю навигацию, surface state и screen components;
- сделать основной экран `tasks`;
- хранить navigation state через простой discriminated union;
- сохранить Telegram auth и текущие API contracts;
- централизовать user-facing error banner/toast.

Не входит:

- новый router;
- глобальный state manager;
- переписывание API.

Acceptance:

- обычный запуск открывает задачи;
- chat start context открывает связанную доску;
- нижняя навигация работает;
- существующие API-функции не потеряны.

### P2. Ввести Refined Editorial UI foundation

**Цель:** реализовать общую визуальную систему один раз.

Scope:

- CSS tokens: surfaces, text, borders, blue primary, coral urgency, section colors, radii, shadows, spacing;
- safe-area handling;
- typography and responsive mobile frame;
- reusable controls: icon button, task glyph, section header, bottom nav, sheet, field row, avatar, badge;
- локальные SVG-иконки без новой dependency;
- reduced-motion и focus-visible;
- минимум 44×44 px для интерактивных targets.

Acceptance:

- shell соответствует `xlomj` на 390×844;
- нет horizontal overflow на 320–430 px;
- интерфейс usable при 200% text zoom;
- значения не кодируются только цветом.

### P3. Доска, поиск и фильтры

**Цель:** дать общий task context до реализации групп.

Scope:

- selector доски в заголовке;
- bottom sheet: все доски, недавние, поиск, управление;
- временный chat-board override;
- поиск и filter sheet;
- chips активных фильтров и `Сбросить`;
- завершённые скрыты по умолчанию;
- миграция существующего per-board filter persistence.

Acceptance:

- выбор сохраняется между запусками;
- chat launch не перезаписывает global choice;
- filter count совпадает с активными условиями;
- API не получает запрос на каждую клавишу без debounce.

### P4. Экран задач: список по срокам и проектам

**Цель:** реализовать одобренный главный экран `xlomj`.

Scope:

- чистые helpers для группировки;
- секции Просрочено/Сегодня/Ближайшие/Без срока;
- alternate grouping по проектам;
- task row;
- completion action;
- empty/loading/error states;
- сохранение grouping и scroll position.

Acceptance:

- задача попадает ровно в одну временную группу;
- completed скрыты по умолчанию;
- срочность и просрочка различаются семантически;
- группы не смешиваются визуально;
- переключение группировки не меняет набор задач.

### P5. Полноэкранное создание задачи

**Цель:** заменить встроенную длинную форму экраном `lZNQ6`.

Scope:

- central `+` route;
- обязательные поля и validation;
- автоматическая доска из контекста;
- board first в global context;
- `Дополнительно` для текущих secondary fields;
- native date/time inputs;
- pending/error/success states;
- optimistic insertion или targeted reload.

Acceptance:

- название и доска валидируются до request;
- ошибка сохраняет введённые данные;
- success возвращает в исходный task context;
- новая задача видна сразу.

### P6. Полноэкранные детали задачи

**Цель:** реализовать экран `irWr4` и убрать prompt-based editing.

Scope:

- sections Главное/Содержание/Обсуждение;
- inline or sheet editing основных полей;
- checklist CRUD;
- comments composer;
- URL/Telegram attachments;
- `•••` для archive/delete/history/recurrence actions;
- возврат с полным восстановлением task context.

Acceptance:

- все текущие collaboration capabilities доступны без `window.prompt`;
- incomplete checklist confirmation сохраняется;
- ошибки действий не закрывают экран и не теряют ввод;
- back восстанавливает scroll/filter/view state.

### P7. Мобильный канбан

**Цель:** реализовать `hOXuP` без четырёх мобильных колонок.

Scope:

- одна активная колонка;
- status tabs и swipe;
- явное изменение статуса;
- optimistic rollback через существующий helper;
- сохранение активной колонки;
- удалить touch long-press drag path с mobile UI.

Acceptance:

- на ширине 320–430 px видна одна колонка;
- свайп не конфликтует с вертикальным scroll;
- статус меняется только после явного действия;
- failed request возвращает исходный статус и показывает ошибку.

### P8. Переименовать `Жду` в `Блокер` во всех поверхностях

**Цель:** синхронизировать product language без изменения DB enum.

Scope:

- web labels;
- Telegram publications;
- notifications;
- tests and fixtures;
- API error copy при необходимости.

Acceptance:

- пользователь нигде не видит `Жду` как статус;
- API/DB продолжают использовать `waiting`;
- исторические данные остаются валидными.

### P9. Структурированные зависимости блокеров

**Цель:** поддержать согласованную blocker model.

Scope:

- migration для task dependency;
- board-scoped FK/validation;
- запрет self-reference и циклов;
- API для выбора task blocker или external reason;
- автоматический переход зависимой задачи в `todo` после completion blocker task;
- assignment notification;
- timeline events;
- корректное поведение archive/reopen.

Acceptance:

- task blocker выбирается только в той же доске;
- cycle возвращает 409 с понятной ошибкой;
- completion атомарно разблокирует dependents;
- повторный webhook/job не создаёт дубль уведомления;
- external blocker снимается только вручную.

### P10. Task deep links

**Цель:** корректно открывать задачу из Telegram publications.

Scope:

- распознавать `task_<board>_<task>` отдельно от invite token;
- авторизовать membership;
- открыть task details в board context;
- корректные 403/404 states;
- сохранить board-link redemption.

Acceptance:

- ссылка из публикации открывает нужную задачу;
- чужая задача не раскрывает данные;
- старые board invite links продолжают работать.

### P11. Корневые настройки и перенос функций

**Цель:** реализовать `mP9O3`, не потеряв существующие функции.

Scope:

- root Settings;
- Workspace: boards/projects/members;
- Automation: recurrences/publications/notifications;
- Account: profile/personal preferences;
- технические значения заменяются понятными controls;
- preview публикаций остаётся доступен на дочернем экране.

Acceptance:

- корневой экран содержит только три раздела;
- все существующие настройки достижимы максимум за 2–3 перехода;
- нет prompt-based configuration;
- права chat admin проверяются только на действиях, где это функционально нужно.

### P12. Telegram theme, accessibility и визуальная стабилизация

**Цель:** довести утверждённый UI до product-ready состояния.

Scope:

- Telegram light/dark theme params;
- системная dark fallback;
- skeleton/loading/empty/error/offline states;
- keyboard and screen-reader pass;
- screenshot checks ключевых экранов;
- device checklist 320/390/430 px.

Acceptance:

- contrast соответствует WCAG AA для основного текста и controls;
- safe areas работают на iOS/Android Telegram;
- screen-reader labels есть у icon-only controls;
- пять канонических экранов проходят visual regression review.

### P13. Release gate

**Цель:** безопасно заменить pilot prototype.

Scope:

- unit, DB isolation, typecheck, build;
- device smoke в Telegram;
- onboarding smoke существующего `@kairostask_bot`;
- create/edit/complete/block/unblock flows;
- publication task-link smoke;
- deploy runbook и rollback check.

Acceptance:

- `npm run test` проходит с `TEST_DATABASE_URL`;
- `npm run typecheck` и `npm run build` проходят;
- production health и Telegram smoke проходят;
- старый UI rollback остаётся доступен до завершения smoke.

## 8. Definition of done для каждого UI Issue

- Реализован только согласованный scope.
- Нет новых prompt/confirm flows.
- Нет новой dependency без доказанной необходимости.
- Добавлен минимальный runnable test для новой логики.
- Typecheck и build проходят.
- Изменённый экран проверен на 390×844 и одной граничной ширине.
- Loading, empty, error и permission state не забыты.
- Copy использует согласованные названия: Новая / В работе / Блокер / Готово.
- PR содержит путь к соответствующему root/PNG из канонического `.pen`.
