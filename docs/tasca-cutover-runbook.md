## 3. Нерешённая Telegram identity (#164)

**Безопасный вариант первого выпуска:** сохранить существующего бота и его username, обновить оформление/обучение и домен; новый кандидат пока не подключать. Это рекомендация, не принятое за владельца решение.

Если нужен именно новый бот, потребуется отдельная реализация и приёмка, а не замена переменной окружения:

- `initData` подписана token конкретного бота; новый token не принимает старые запуски. Это отрицательный сценарий rehearsal, не обход защиты.
- Чаты и доступ к участникам не переносятся. Потребуются добавление нового бота, проверка администраторов и явно управляемый переход старого. Текущая обработка удаления бота замораживает доску.
- Личные уведомления требуют, чтобы пользователь сам запустил нового бота. Нельзя обещать доступ к прежним DM.
- Telegram `file_id` привязан к боту: ранее загруженные вложения требуют отдельного решения доступности, старый token нельзя просто удалить.
- Старые t.me-закрепы, приглашения и task links должны открывать правильную identity; Telegram redirect не предполагается.
- В БД есть состояние доставки приветствий и дедупликации. Два бота не должны одновременно запускать публикации и конкурировать за один логический send; секреты/webhooks/update IDs требуют разделения по identity.

Пока владелец не выбрал сценарий и совместимость не доказана, новый token хранится без подключения к runtime. #164 блокирует #138.

## 4. Выполненная локальная репетиция

`apps/api/test/cutover.test.ts` запускается только с loopback `tasca_rehearsal_*` БД и явным `ROLLBACK_APP_MODULE`. Синтетические данные остаются для dump/restore; production URL guard отклоняет.

1. Настоящий собранный код `98fb9fc`, отдельная PostgreSQL 14.23 UTF-8, два HTTP proxy на loopback. Авторизация синтетическим initData, личная доска, задача до переключения, MCP-ключ, посторонний пользователь.
2. Оба proxy переключены на кандидат. Проверены оба HTTP-origin, GET health, POST webhook без отправки сообщения, те же user IDs, cookie flags, права и отказ постороннему, Host/Origin, отсутствие CORS/redirect, реальный MCP SDK с ранее созданным ключом.
3. Через новый MCP endpoint создана задача **после переключения**.
4. Proxy возвращён на настоящий код `98fb9fc` с прежней конфигурацией и **той же БД**. Старая и новая задачи доступны с прежним MCP-ключом, права сохранены, постороннему отказано. Снимок БД для rollback не восстанавливался.
5. После rollback выполнены `pg_dump -Fc`, восстановление в отдельную новую БД и сравнение row counts + полных row fingerprints всех 20 public tables. Новая задача сохранена. Evidence: `artifacts/evidence/issue-137-restore-verification.json`.

Команда теста после подготовки отдельной БД и сборки старой версии:

```bash
TEST_DATABASE_URL=postgresql://tasca_test@127.0.0.1:5499/tasca_rehearsal_137 \
ROLLBACK_APP_MODULE=/absolute/path/to/rollback/apps/api/dist/app.js \
npm run test:cutover
```

Это **не** проверка production PostgreSQL 17, TLS, Telegram devices, DNS или multi-bot migration. Старый код после rollback не поддерживает новый MCP alias: доказана работоспособность прежнего входа и сохранность новых данных, не доступность обоих origin на старом коде.

## 6. Единственный финальный выпуск (#138)

После выполнения gates и подтверждения точного пакета:

1. Сверить immutable release/rollback SHA и приватный snapshot. Backup/restore уже проверены. DB/volume/пользователи/история/секреты остаются прежними.
2. Настроить валидный TLS/proxy для обоих host. Действующие API/MCP/webhook не redirect-ить и не останавливать ради лендинга. Не включать wildcard origin/CORS.
3. Выпустить собранную ревизию с согласованными PUBLIC_URL/ALIASES и **выбранной** Telegram identity. Миграции — только штатные и отдельно проверенные, не тестовые команды.
4. Проверить local/public health и ответы двух host; затем применить ровно согласованные bot fields/commands/avatar/menu/Main Mini App/webhook. Каждое поле прочитать обратно. Не выполнять `drop_pending_updates`.
5. Проверить старые и новые обычные ссылки, Mini App, приглашение, task deep link, initData, права, отсутствие HTML на API/MCP, прежний MCP-ключ и scope. Проверить `/start`, `/help`, создание первой задачи, сохранение после reopen, одну разрешённую доставку и одну публикацию без дубля.
6. Restart gate: одна recurrence и один scheduled report возникают ровно один раз. Проверить ошибки/очереди без вывода чувствительных данных.
7. Наблюдение: сразу после выпуска и restart; повтор через 15 минут и 24 часа. Оператор фиксирует actual SHA, время, результаты readback, HTTP error rate, delivery failures и backlog. Пороги должны сравниваться с предрелизным baseline, а не выдумываться после ошибки. Наблюдение не считается завершённым заранее.

## 7. NO-GO и rollback

NO-GO: TLS failure, неизвестная bot identity, потерянная старая ссылка, неподтверждённый backup/restore, недоступный оператор/rollback, failed auth/permissions/MCP или обязательный device gate. При неопределённой отправке не повторять сообщение автоматически.

При регрессии остановить дальнейшие переключения. Вернуть предыдущую конфигурацию, bot fields и webhook из приватного snapshot, при необходимости предыдущую совместимую версию приложения. **Оставить ту же БД и новые записи.** Не выполнять downgrade или restore старого dump поверх живых данных. Проверить созданную после cutover задачу и её права через прежний вход.

Если прежняя версия не знает aliases, новый MCP-host временно должен возвращать явный 503, а не пересылать Bearer на другой origin. Вернуть клиенту прежний endpoint; новый домен не удалять. Возврат профиля/username нового бота не считается обратимым без отдельной проверенной процедуры #164.

Restore нужен только для подтверждённого повреждения данных: отдельная БД, сверка и перенос записей после backup по отдельному recovery-плану. Исторический dump не является обычным откатом ребрендинга.
