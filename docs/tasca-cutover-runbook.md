## 3. Согласованный переход на нового бота (#164)

Владелец подтвердил: `@tasca_app_bot` — полностью новый бот; работает только команда. Владелец добавляет его в прежний чат, получает автоматическое приветствие с принятой картинкой v0.7 и кнопкой в прежнюю доску, затем заменяет закреп. Сохранение старых Telegram-ссылок из переписки не требуется. Прежние данные и права сохраняются; предварительный `/start` в личке каждому участнику для группового входа не нужен.

Оставшиеся технические границы и приёмка:

- `initData` подписана token конкретного бота; новый token не принимает старые запуски. Это отрицательный сценарий rehearsal, не обход защиты.
- Чаты и доступ к участникам не переносятся. Потребуются добавление нового бота, проверка администраторов и явно управляемый переход старого. Текущая обработка удаления бота замораживает доску.
- Личные уведомления требуют, чтобы пользователь сам запустил нового бота. Нельзя обещать доступ к прежним DM.
- На проверенном снимке нет Telegram file_id, поэтому перенос таких файлов не требуется. Это не проверка содержимого URL-вложений и не разрешение удалять старый token; перед переключением повторить инвентаризацию.
- Новый launch link отзывает прежний launch link существующим механизмом. При rollback нельзя обещать автоматическое восстановление старого закрепа: получение рабочего входа старого бота необходимо отдельно проверить.
- Приветствия и ответы на команды разделены по стабильной bot identity; старые записи сохранены. Локальный regression проверяет прежнюю доску/задачи/права, повтор события, смену токена и соседний путь команд. Два runtime/scheduler одновременно не поддерживаются этим изменением. Старые webhook-события не должны обрабатываться как события нового бота.

Сценарий выбран, но live/device приёмка и полный rollback нового Telegram-входа ещё не доказаны. Новый token пока хранится без подключения к runtime. #164 продолжает блокировать #138.

## 6. Единственный финальный выпуск (#138)

После выполнения gates и подтверждения точного пакета:

1. Сверить immutable release/rollback SHA и приватный snapshot. Backup/restore уже проверены. DB/volume/пользователи/история/секреты остаются прежними.
2. Настроить валидный TLS/proxy для обоих host. Действующие API/MCP/webhook не redirect-ить и не останавливать ради лендинга. Не включать wildcard origin/CORS.
3. Выпустить собранную ревизию с согласованными PUBLIC_URL/ALIASES и **выбранной** Telegram identity. Миграции — только штатные и отдельно проверенные, не тестовые команды.
4. Проверить local/public health и ответы двух host; затем применить ровно согласованные bot fields/commands/avatar/menu/Main Mini App/webhook. Каждое поле прочитать обратно. Не выполнять `drop_pending_updates`.
5. Проверить старый и новый HTTP-origin, новые Telegram-ссылки, Mini App, приглашение, task deep link, initData, права, отсутствие HTML на API/MCP, прежний MCP-ключ и scope. Проверить `/start`, `/help`, создание первой задачи, сохранение после reopen, одну разрешённую доставку и одну публикацию без дубля. Старые Telegram-ссылки не являются критерием успешного перехода.
   Обучение #135: из `/start` пройти пять шагов для каждого сценария, проверить «Назад», «Пропустить», повтор через `/help`, двойное нажатие и финальный вход. `callback_query` должен присутствовать в readback webhook; наличие кода без этой настройки не означает рабочие кнопки.
6. Restart gate: одна recurrence и один scheduled report возникают ровно один раз. Проверить ошибки/очереди без вывода чувствительных данных.
7. Наблюдение: сразу после выпуска и restart; повтор через 15 минут и 24 часа. Оператор фиксирует actual SHA, время, результаты readback, HTTP error rate, delivery failures и backlog. Пороги должны сравниваться с предрелизным baseline, а не выдумываться после ошибки. Наблюдение не считается завершённым заранее.

## 7. NO-GO и rollback

NO-GO: TLS failure, несовпадение фактической bot identity с согласованной, потерянный обязательный HTTP/MCP-вход, неподтверждённый backup/restore, недоступный оператор/rollback, failed auth/permissions/MCP или обязательный device gate. При неопределённой отправке не повторять сообщение автоматически.

При регрессии остановить дальнейшие переключения. Вернуть предыдущую конфигурацию, bot fields и webhook из приватного snapshot, при необходимости предыдущую совместимую версию приложения. **Оставить ту же БД и новые записи.** Не выполнять downgrade или restore старого dump поверх живых данных. Проверить созданную после cutover задачу и её права через прежний вход.

Если прежняя версия не знает aliases, новый MCP-host временно должен возвращать явный 503, а не пересылать Bearer на другой origin. Вернуть клиенту прежний endpoint; новый домен не удалять. Возврат профиля/username нового бота не считается обратимым без отдельной проверенной процедуры #164.

Restore нужен только для подтверждённого повреждения данных: отдельная БД, сверка и перенос записей после backup по отдельному recovery-плану. Исторический dump не является обычным откатом ребрендинга.

Имя/описания/команды нового бота уже совпадали с утверждёнными — не применять их повторно без обнаруженного изменения. Эти значения не являются текущим readback.
- Ответ поддержки провайдера не является условием подготовки или выпуска. Реальная доставка и восстановимый старый вход являются условиями; прежний timeout нельзя считать ни устранённым, ни доказательством вины провайдера.

### 8.2. До разрешённого окна

1. Назначить оператора server/API/rollback и владельца BotFather, закрепа и device-проверок. Проверить доступность старого бота в прежней группе и его права. Не удалять старого бота из группы и не отзывать token: удаление создаёт событие заморозки общей доски.
2. Прочитать разрешённые `getMe`, `getWebhookInfo`, `getChatMenuButton`; отдельно подтвердить в BotFather Main Mini App URL обоих ботов. `has_main_web_app=true` не доказывает правильный URL. Сохранить обратные значения приватно; не печатать env, токены, cookie или полный Bot API response. Не использовать `getUpdates` для диагностики.
3. Проверить старый Telegram-вход и получение нового приглашения администратором через существующий `POST /api/boards/:id/invites`. Требуются реальная авторизация администратора и доступ старого бота к `getChatMember`; синтетический тест ниже их не заменяет. Администратор должен иметь прямой вход через Main Mini App/menu и список своих досок, не только старый закреп.
4. Подготовить immutable candidate image, прежний image, защищённые old/new env и proxy-снимки. Сохранить прежние `DATABASE_URL`, `SESSION_SECRET`, volume и MCP grants. Новый `WEBHOOK_SECRET` должен отличаться от старого; `getWebhookInfo` не возвращает secret, поэтому старый сохраняется из разрешённой конфигурации. Перед переключением сверить 17 migration-файлов; их изменение требует новой проверки совместимости.
5. Снять агрегатный baseline ошибок, очередей, вложений и будущих публикаций. Классифицировать прежний pending notification, `sending` и неопределённые исходы, не сбрасывая статусы и не переотправляя. У приложения нет режима «запустить без отправителя»: publication scheduler начинает работу сразу, recurrence — при старте. Поэтому запуск нового runtime одновременно разрешает обработку существующих расписаний; адресаты и окно должны быть согласованы заранее.
6. Подтвердить тестовые аккаунты/группу, iOS/Android/Desktop, живой MCP-клиент, разрешённые доставки и наблюдение сразу/15 минут/24 часа. Выполнить обязательные предрелизные device/client gates #140/#164; постдеплойные пункты остаются после переключения. Согласовать срок сохранения старого HTTP/MCP-origin и bot rollback-доступа; автоматического отключения нет.
7. Получить GO именно на этот пакет с заполненными оператором, image ID, внешними значениями, приёмкой и планом остановки. Известный Fastify advisory остаётся отдельным неустранённым риском; зафиксировать решение владельца, не считать молчаливо принятым.

### 8.3. Переключение после GO

Решение владельца от 2026-10-02 для пакета source `7eec2b35815be558dcbc2664e8497c50de2d0b54`, image `sha256:0db53e919752e9b1c3469e63468ffef197b3ad1cca725e240f3e342989519f81`: получен явный GO; отдельно принят выпуск с Fastify 5.12.4 в проверенной HTTP/1.x-конфигурации. Владелец явно разрешил перенести живое получение откатного приглашения и iOS/Android/Desktop-приёмку из предварительных gates в приёмку после переключения. Это изменение порядка, не отмена проверок и не PASS полного Telegram rollback. Старый вход и видимость прежних задач подтверждены владельцем, оба бота — администраторы; старый image, bot credential и текущая БД сохраняются. #138/#164/#140 не закрываются до обязательной приёмки. Остальные условия сохранности данных, readback и остановки при регрессии остаются в силе.

Каждый шаг выполняется последовательно. Не продолжать после неуспешного readback. Bot API вызывается безопасным инструментом без токена в shell arguments или логах; тела ниже задают параметры, а не разрешают вызовы.

1. В разрешённом окне владелец добавляет нового бота в согласованные прежние группы и обеспечивает нужные права **до запуска нового sender**. Пока новый webhook пустой, событие добавления ожидает доставки; старый бот остаётся в группе. Не добавлять/удалять ботов повторно ради повторной отправки приветствия.
2. Снять свежий backup и повторить короткий preflight. Завершить или классифицировать in-flight отправки. На старом боте вызвать `deleteWebhook` с `{"drop_pending_updates":false}`; `getWebhookInfo.url` должен стать пустым. Очередь не сбрасывать и не подтверждать через polling.
3. Остановить **только** старый app (`docker compose stop app`), дождаться завершения процесса и убедиться, что отправителя больше нет. Оставить db и volume на месте. Отключение webhook не отзывает уже начавшиеся запросы, а остановка scheduler не доказывает результат отправки: неизвестные исходы требуют проверки перед продолжением.
4. Установить заранее проверенный candidate image и new env, оба proxy направить на одно приложение без redirect. Проверить `nginx -t` до разрешённого reload. Запустить только app из подготовленного immutable image (`docker compose up -d --no-deps --no-build app` с заранее проверенной image-конфигурацией). Не применять этот вызов с прежней/неизвестной Compose image-настройкой; не запускать второй app, не пересоздавать db.
5. Проверить local/public health обоих host, единственный app/scheduler, API/MCP без HTML/redirect. Старый webhook secret должен получать 401 на новом runtime. Это проверяется безопасным POST без пользовательского update; не отправлять синтетический `my_chat_member` в production.
6. Установить согласованный Main Mini App URL в BotFather и default menu нового бота: `{"menu_button":{"type":"web_app","text":"Открыть задачи","web_app":{"url":"https://tasca.kairos-ai.ru"}}}`. Прочитать menu обратно, отдельно проверить URL и запуск Main Mini App. Старые menu/Main Mini App оставить без изменений для отката.
7. На новом боте вызвать `setWebhook`: `url=https://tasca.kairos-ai.ru/api/telegram/webhook`, отдельный сохранённый `secret_token`, `max_connections=40`, `allowed_updates=["message","my_chat_member","callback_query"]`, `drop_pending_updates=false`. Сразу прочитать точный target через `getWebhookInfo`.
8. Проверить реальную доставку накопленного события добавления, одно приветствие с кнопкой в прежнюю доску; владелец меняет закреп. Не вызывать повторную отправку при неизвестном исходе. Затем выполнить полный чек-лист #164 и §§6–7, проверить старый MCP-ключ, права, вновь созданную задачу, restart и наблюдение. Снижение pending само по себе не доказывает обработку.

Ограничение Telegram: updates хранятся не дольше 24 часов; `drop_pending_updates=false` не продлевает этот срок. Входящая очередь остановленного старого бота не обслуживается после cutover. Не обещать её бессрочную сохранность; до окна обеспечить обработку старого backlog и сообщить команде о переходе. Изменение `allowed_updates` также не исключает уже созданные updates. Источник: [Bot API: Getting updates, setWebhook, deleteWebhook](https://core.telegram.org/bots/api#getting-updates), прочитан 2026-10-02.

### 8.4. Обратный порядок при регрессии

1. Прекратить дальнейшую приёмку и изменения. Новый `deleteWebhook({drop_pending_updates:false})`, затем readback пустого URL. Дождаться/классифицировать in-flight обработку и остановить только новый app. Не сбрасывать очереди или delivery receipts.
2. Вернуть сохранённые старые env и immutable image, прежний proxy; оставить **ту же текущую БД**. Новый HTTP-host при несовместимости старого кода возвращает 503, не redirect с Authorization. Проверить конфигурацию proxy перед reload; запустить единственный старый app без build и без пересоздания db.
3. Проверить health старого origin, старый MCP-ключ и данные, созданные после переключения. Новый webhook secret должен отвергаться старым runtime. Только после этого вернуть старый webhook по snapshot: URL, старый secret, `allowed_updates`, `max_connections` и дополнительные параметры, если они были настроены; `drop_pending_updates=false`. Нельзя получить прежний secret из Bot API readback.
4. Восстановить только действительно изменённые menu/Main Mini App нового бота из snapshot. Старый бот всё ещё должен присутствовать в группе. Проверить старый Main Mini App/menu и новую авторизацию старой identity; сохранить новые задачи и прежние права.
5. **Не возвращать старый закреп вслепую:** новый launch link уже отозвал прежний. Администратор открывает старый Mini App, выбирает прежнюю доску и через существующий `POST /api/boards/:id/invites` получает новое приглашение на `@kairostask_bot`. Проверяет фактическое открытие и права, затем заменяет закреп вручную. Не редактировать SQL links, не сбрасывать приветствия и не добавлять бота повторно. Если администратор не может войти или получить приглашение, Telegram rollback не принят.
6. Убедиться, что новая задача и права сохранились через восстановленный вход; выполнить разрешённую доставку старого бота, наблюдение и readback всех изменённых targets. Не удалять нового бота из группы в середине отката: его события остаются в отдельной очереди и не должны попасть в старый обработчик.

### 8.5. Проверенная локальная граница

В `test:cutover` добавлен второй сценарий: captured старый API создаёт активную группу, новый bot token входит в ту же доску и создаёт задачу, затем captured старый API снова принимает старую identity и выдаёт рабочее новое приглашение. Проверяются отказ чужой initData, разные webhook secrets (включая запоздалое удаление), отсутствие повторного приветствия, отозванный прежний launch link, неизменные memberships, отказ постороннему и сохранность обеих задач без restore.

Это реальная отдельная PostgreSQL с синтетическими данными и настоящим captured compiled API, **но Telegram/getChatMember/отправки замоканы**. Тест не доказывает BotFather, HTTPS-доставку, наличие прав в реальной группе, запуск Docker image или физические устройства. Внешняя приёмка и отдельный GO остаются обязательными. В этом этапе runtime, webhook, menu, DNS, proxy и production-БД не менялись.
