## 1. Зафиксированные решения владельца

- `importance` и `urgency` независимы: `true`, `false`, `null` («не оценено»).
- Старый `urgent`: `importance=null`, `urgency=true`. Старый `normal`: оба `null`.
- Новый клиент создаёт задачу без оценки, если пользователь её не задал. Дедлайн ничего не присваивает.
- Хотя бы одно неизвестное значение означает «Не разобрано». Известная часть оценки остаётся видимой.
- Окно «Приоритет»: два вопроса с тремя вариантами; независимое изменение и общий сброс.
- «Не разобрано» — отдельный сворачиваемый блок перед оценёнными группами. Порядок последних: важное срочное; неважное срочное; важное несрочное; неважное несрочное.
- Внутри блока: ближайший срок, затем задачи без срока; при равенстве более старые задачи, затем ID.
- `waiting` остаётся в своей группе с пометкой «Блокер». `done` показывается только при явном соответствующем фильтре. Архив не входит в матрицу активных задач.
- Мобильная матрица: единая сетка 2×2, важность по столбцам, срочность по строкам. В каждом квадранте до трёх задач и кнопка «Ещё N», если их больше; названия категорий в ячейках и отдельный список снизу не дублируются. Это уточнение владельца заменяет исходный вариант плиток со счётчиками. При крупном тексте одна колонка с названиями категорий вместо осей. Фильтры и поиск общие со списком.
- Ни оценка, ни название категории не меняют статус, срок, исполнителя или архив.

Принятый HTML-макет: `artifacts/ux/issue-177/index.html`. Кнопка «Ещё N» открывает полный список категории в отдельном окне, сохраняя поиск, фильтры и порядок; из карточки можно вернуться в этот список. Владелец принял итоговый макет после этих изменений. HTML использует вымышленные данные, память страницы и имитацию состояний; он не является кандидатом приложения или доказательством device-проверки.

## 3. Канонический формат

В таблицах `tasks` и `recurrence_templates`: nullable boolean `importance`, `urgency`, default `NULL`. В HTTP и MCP используются те же имена. Категория вычисляется, не хранится как третье поле приоритета.

В запросе:

- отсутствие поля означает «не менять» в PATCH и `null` при создании;
- `false` означает явное «нет»;
- `null` означает явный сброс только этого признака;
- строки, числа, массивы и объекты вместо boolean/null отклоняются на границе;
- сброс всей оценки — один запрос `{importance:null, urgency:null}`, одна транзакция и одна новая revision;
- нельзя использовать `input.urgency ?? task.urgency`: это уничтожит семантику явного `null`. Проверять `=== undefined`.

Пример нового PATCH (формат проекта, пока не реализован):

```json
{"importance":true,"expectedVersion":"12"}
```

Срочность, дедлайн, статус и остальные поля этим запросом не затрагиваются. Для нового MCP вызова поля находятся в `changes`; `requestId` и `expectedVersion` сохраняют действующий смысл.

В DTO возвращать оба признака, включая `null`. Старое `priority` временно остаётся для совместимости: `urgent`, только если `urgency=true`; иначе `normal`. Старые клиенты не умеют показывать «не оценено», поэтому эта проекция намеренно не является полной оценкой. Новый клиент не восстанавливает каноническую срочность из legacy-проекции.

## 4. Существующие данные, старые клиенты и конфликт значений

### Миграция

Добавить оба nullable-поля к задачам и шаблонам. Для существующих `urgent` заполнить только `urgency=true`; для `normal` оставить `null`. Прежнее `priority` и исторические audit JSON не удалять и не переписывать. Повторный запуск миграции не должен снова заполнять сброшенное позднее `urgency=null`: data backfill выполняется ровно один раз под штатным учётом миграций, не при каждом запуске приложения.

Проверить revision-trigger: технический backfill не должен выглядеть как действие пользователя, но старый optimistic snapshot после перехода обязан обнаруживаться. Способ поднятия revision и момент обновления клиента нужно проверить на реальной схеме в изолированной БД; не утверждать здесь уже выполненную миграцию.

### Предлагаемый адаптер legacy-записи

Применяется внутри общей транзакции после проверки доступа и версии. Не требует отдельной бизнес-логики для web и MCP.

| Вход | Создание | PATCH существующей записи |
| --- | --- | --- |
| Оценка и `priority` отсутствуют | Оба признака `null` | Оба признака сохраняются |
| Только `priority=urgent` | `importance=null`, `urgency=true` | Только срочность меняется на `true`, если это не echo текущей проекции |
| Только `priority=normal` | Оба признака `null` | Если текущая проекция уже `normal`, это echo/no-op. Переход `urgent` в `normal` означает `urgency=false`, важность сохраняется |
| Канонические поля без `priority` | Указанные значения; отсутствующие `null` | Меняются только явно указанные поля |
| Канонические поля вместе с `priority` | Проверяется согласованность с итоговой проекцией | Сначала вычисляется итог из текущих и явно переданных полей, затем проверяется legacy-проекция |
| Противоречивые канонические поля и `priority` | 400 / MCP `INVALID_ARGUMENT`, без записи | Та же ошибка, без частичного изменения |

Зачем no-op при неизменившемся `normal`: старый клиент не отличает `urgency=false` от `urgency=null` и может отправить `normal` вместе с другим изменённым полем. Такой echo не должен превращать неизвестную срочность в явное «нет» или стирать ранее заданную важность.

### Принятая граница совместимости

**Без версии невозможно отличить намеренное изменение старого `priority` от устаревшего echo.** Существующий HTTP допускает PATCH без `expectedVersion`; MCP `update_task` его уже требует.

Безопасный предлагаемый переход: legacy-PATCH без версии разрешает неизменившийся `priority` как no-op и изменение независимых полей. Если `priority` меняет текущую проекцию, отклонять весь запрос с 409 и понятным требованием перечитать задачу/обновить клиент. Не применять часть payload. Для канонического изменения оценки требовать `expectedVersion`; после проверки версии legacy-переход разрешён по таблице выше.

Владелец принял ограничение: **изменение оценки без версии задачи отклоняется; чтение и независимые поля не ограничиваются этим правилом**. Старые интеграции для изменения оценки потребуется обновить. Описанный выше ответ 409, обработка no-op и транзакционные детали остаются инженерным проектом, подлежащим реализации и проверкам; согласование не доказывает их работу. Шаблоны повторений требуют такой же защиты, см. раздел 7.

## 5. Сохранённые и новые фильтры

Новый UI/MCP фильтр каждого признака: `any | true | false | unassessed`. Wire-значение `unassessed` означает SQL `IS NULL`, а отсутствие фильтра — отсутствие условия. В HTML-кандидате значение `null` в `<select>` — только локальное представление этой опции, не утверждение wire-формата.

«Не разобрано» — условие `importance IS NULL OR urgency IS NULL`, не третий приоритет. Оно сочетается с другими фильтрами через AND. Например, «Не разобрано» + «Срочные» даёт задачи с известной срочностью и неизвестной важностью. Матрица и её счётчики используют один и тот же отфильтрованный набор, без обхода membership/board access.

При восстановлении прежнего сохранённого состояния:

- пустой `priority` превращается в отсутствие условий оценки;
- `urgent` сохраняется как `urgency=true`;
- `normal` остаётся legacy-условием «не помечена срочной»: `urgency IS NOT TRUE`, то есть `false` **или** `null`. Нельзя молча заменить его на новый явный фильтр «Несрочная» (`false`);
- сохраняются scope, project, assignee, status, deadline, unassigned и search;
- новый фильтр оценки заменяет legacy-условие, а не складывается с невидимым старым ограничением;
- legacy-фильтр виден пользователю как «Без отметки “Срочная”», не как «Несрочные»;
- invalid view/grouping сбрасывается отдельно от валидных фильтров, если это нужно для миграции состояния; не стирать всё сохранённое состояние из-за добавления новой опции;
- компоновка полной панели остаётся задачей #181. Этот пакет определяет значения и их смысл.

## 6. Детерминированный порядок и MCP-пагинация

Ранг: `unassessed`, затем четыре принятых категории. Для сравнения внутри группы предлагается единый ключ:

1. Наличие срока: заданный раньше отсутствующего.
2. Эффективный момент срока UTC. Для timestamp используется сам timestamp; date-only представляется началом следующих суток в `deadline_timezone` (exclusive day-end). Это согласуется с тем, что задача на дату не просрочена до окончания её дня. Сортировка не меняет отображаемую дату и срочность.
3. `created_at` по возрастанию.
4. UUID по возрастанию в одинаковом байтовом/каноническом порядке.

Date-only tie-break является предложенным инженерным уточнением «ближайшего срока»; проверить в общей матрице часовых поясов, включая DST. Для одинакового результата web и SQL не терять точность timestamp при сериализации: передавать стабильный sort key либо нормализованные временные строки полной точности. Нельзя ограничиться `Date` с миллисекундами, если SQL различает микросекунды.

Web получает `created_at`/ключ сортировки в своём типе, которого сейчас нет в `Task`, хотя DB уже выбирает `created_at`. Общая фильтрация выполняется до группировки, список и матрица сортируются одинаково. Внутри «Не разобрано» известная срочность показывается, но не меняет согласованный внутригрупповой порядок.

MCP: сохранить существующий default-порядок `created_at DESC,id DESC`; добавить явный `sort=priority`, не ломая молча старую пагинацию. Для него курсор должен включать полную границу `(rank, has_no_deadline, effective_deadline, created_at, id)`, направление сравнений и fingerprint всех фильтров/сортировки. Сначала SQL-права и фильтры, затем сортировка и LIMIT; нельзя сортировать отдельно уже выбранную страницу.

Старые курсоры default-выдачи должны сохранять формат/fingerprint: новый default в Zod не должен неявно менять хеш прежнего запроса. При изменении условий курсор отклоняется. Для неизменившегося набора проверяются отсутствие пропусков/дублей между страницами, включая одинаковые сроки/created_at. Курсор не обещает snapshot isolation между отдельными запросами при параллельном редактировании задач; при изменившемся наборе клиент начинает новый обход.

## 7. Автосохранение, повторения, история, повторы запросов

- Минимальный PATCH только изменённых признаков. `importance` и `urgency` — отдельные группы merge/conflict. Изменение срока не отправляет оценку. Сброс двух признаков атомарен.
- В HTML окно держит локальный выбор до «Применить»; крестик, «Отмена» и Escape ничего не меняют. После применения в приложении используется существующий autosave/expectedVersion, не второй механизм сохранения.
- Ошибка не помечается как «Сохранено». При потере ответа выполнить readback и reconciliation; если значения уже приняты сервером, не повторять старый snapshot поверх новой версии. Различать отсутствие ответа и гарантированный отказ.
- MCP сохраняет receipts: тот же `requestId` с теми же аргументами повторяет намерение, изменённые аргументы дают конфликт. Изменение defaults schemas не должно ломать хеш ранее выданного receipt. Сначала проверяется старая идентичность намерения, потом адаптация к новым колонкам; учесть текущие `.default(normal)` при create. Аналогично не менять legacy `create_request_hash` HTTP ретрая задним числом.
- Audit before/after включает новые признаки. Исторические события с `priority` показываются как историческая отметка, а не выдуманная важность. Migration не отправляет assignment notifications.
- Новые экземпляры серии копируют оба признака с шаблона. Изменение экземпляра не меняет будущие задачи без явного действия. Scheduler не вычисляет срочность из даты.
- В `updateTaskAndFuture` оба признака входят в ограниченный набор общих полей; задача и шаблон меняются одной транзакцией. Ошибка доступа/версии шаблона откатывает изменение задачи.
- Предлагается добавить revision к шаблону и отдельный `expectedRecurrenceVersion` для изменения будущей серии. Снимок для подтверждения включает эту версию; нельзя сравнивать только task revision. Названия входов и выбор trigger проверить на итоговой схеме. Старый writer без версии не должен молча перезаписывать новую оценку шаблона; граница из раздела 4 распространяется и на него.
- Отмена подтверждения будущих повторов не откатывает уже независимо сохранённую карточку и не меняет серию; это должно быть явно отражено в UI.
