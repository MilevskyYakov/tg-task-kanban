# #178 — безопасное обновление MCP-подключений

Этот документ — инструкция для будущего согласованного релиза #175, не разрешение деплоя. Действующий ключ владельца, его Hermes, production-БД и Telegram-аккаунт при локальной реализации не используются.

## Пользователю после выпуска

1. Откройте «Настройки → Аккаунт → Подключения» и нужное подключение. Старые подключения сохраняют прежний ключ, выбранные доски и режим; автоматически расширять их не требуется.
2. Нажмите «Редактировать». Название, список досок, read/write и способ выбора меняются без смены ключа. Перед сохранением проверьте добавленные/исключённые доски и появление права записи. Отмена не выдаёт доступ.
3. «Все мои текущие и будущие доски» включает личные доски. Это явный выбор, не значение по умолчанию. Текущий состав показан в форме и деталях. Права чтения/изменения распространяются и на новые доски.
4. Потеря членства прекращает доступ. Повторное вступление само его не возвращает, даже если между выходом и возвращением клиент не обращался к серверу. В деталях all указаны исключённые после возвращения доски. Для явного восстановления выберите режим выбранных досок и подтвердите нужный список; затем при необходимости отдельно подтвердите all. Это не восстанавливает доступ других подключений.
5. После изменения прав запросите список досок снова. Если клиент кэширует tools/list, переподключите MCP-сервер или перезапустите клиент. Новый ключ для этого не нужен. Старый кэш write-инструментов не обходит серверный запрет после понижения до чтения.
6. При конфликте параллельного изменения приложение оставляет черновик на экране. Это относится и к изменению доступа к доскам после открытия формы: потеря членства и повторное вступление не позволяют вернуть прежний доступ обычным переименованием. Откройте текущие настройки явным действием, сравните их и повторно внесите нужные изменения. Для восстановления исключённой доски выберите её заново и проверьте, что она перечислена в «Добавятся». Автоматического слияния или перезаписи нет.

## Перевыпуск — отдельное действие

- Используйте «Перевыпустить ключ» только намеренно: после подтверждения старый ключ перестаёт работать. ID, имя, права, задачи и их история сохраняются.
- Сохраните новый ключ из одноразового экрана в своём менеджере паролей. Обновите поле авторизации существующего подключения клиента тем же безопасным способом, которым ключ вводился первоначально. Не вводите ключ в чат, URL, команду с историей shell или файл репозитория.
- Адрес сервера остаётся прежним. Повторно прочитайте список досок из клиента. Доступность и команды конкретной версии клиента сверяйте с его текущей документацией; не изменяйте профиль владельца автоматически.
- Если ответ потерян, нажмите «Проверить результат»: приложение повторит прежний requestId, а не выпустит ещё один ключ. Сервер вернёт либо единственный успешный результат, либо сообщение «Ключ создан, но не был получен». Повторно показать секрет невозможно.
- После подтверждённого потерянного результата можно отдельно согласиться на ещё один перевыпуск или отозвать доступ. Не считать timeout доказательством, что старый ключ работает.
- Отзыв также требует подтверждения. Он не удаляет задачи или историю и не отменяет уже прочитанные клиентом данные. Отозванное подключение не редактируется и не перевыпускается; для нового доступа создайте другое.

## Оператору перед выпуском #175

1. Соберите единую согласованную ревизию. Повторно проверьте интеграцию #176 (все пути удаления общего membership, новая chat-доска) и #177 (общий `mcp.ts` и schemas), затем передайте итоговые экраны в #182. Имя миграции `016_mcp_lifecycle.sql` необходимо сверить с параллельными миграциями; один номер сам по себе не является резервированием.
2. Пройдите общий release-runbook и gate #175: отдельное разрешение, проверка внешнего автодеплоя, резервная копия и тест её восстановления, точная версия, единый план обновления. Не запускайте второй poller/scheduler и не меняйте Telegram transport ради MCP.
3. Примените все миграции сначала к отдельной тестовой БД. В общем кандидате #175 runner из #176 ведёт журнал полных имён файлов: при первом запуске на legacy-БД применяет исторические SQL, при повторном пропускает записанные. Новая MCP-миграция транзакционна: selected по умолчанию, revision, журнал membership losses, secret-free lifecycle receipts. Она не переписывает существующие ключи/grants/tasks/receipts. Отдельная миграция оценки #177 сохраняет содержание задач, но её backfill закономерно увеличивает task revision один раз. Создание all допускает ноль текущих досок; selected edit также может исключить последнюю доску.
4. Отдельно проверьте старую схему с данными на новой пустой disposable БД:

   ```sh
   MCP_MIGRATION_DATABASE_URL="<DSN пустой тестовой БД>" npm exec -- tsx apps/api/test/mcp-migration.ts
   ```

   Скрипт отказывается от непустой БД. Он применяет старые миграции, создаёт синтетический legacy fixture без новых task writers, применяет MCP SQL и настоящий общий runner, затем проверяет отсутствие изменений при повторном запуске и прежний ключ через реальный HTTP/SDK. Проверяется также ровно одно ожидаемое увеличение task revision при assessment backfill. Скрипт не предназначен для production и оставляет тестовые данные для проверки.
5. Полная локальная приёмка:

   ```sh
   DATABASE_URL="$TEST_DATABASE_URL" npm run migrate
   npm run test
   npm run lint
   npm run typecheck
   npm run build
   npm run test:visual
   git diff --check
   ```

   `TEST_DATABASE_URL` должен указывать только на изолированную тестовую БД. Без него DB gate падает. `PLAYWRIGHT_PORT` выбирает свободный локальный порт. Если штатный Chromium не установлен, `PLAYWRIGHT_CHANNEL=chrome` использует установленный Chrome с отдельным временным профилем Playwright, не личным профилем. Это не Telegram/device-приёмка.
6. После отдельного разрешения обновляйте миграции, API и web как один согласованный релиз. Между включением all и новым API не допускайте старые экземпляры приложения: старый код понимает только явные grants и не реализует новый lifecycle. Не включайте новые права в смешанной версии серверов.
   Edit требует и `expectedVersion`, и `expectedAccessVersion` из текущего DTO. Кешированная предварительная версия UI #178 без второго поля получит безопасный отказ; её нужно перезагрузить, а не ослаблять серверную проверку. Эта защита не требует дополнительной миграции и не меняет MCP Bearer или протокол инструментов.
7. Post-deploy readback — точная версия, штатные проверки и разрешённое отдельное тестовое подключение. Не перевыпускайте ключ Якова ради smoke. Реальный клиент и Telegram/device проверяются только в отдельно разрешённом тестовом контуре.

## Откат

Новый API требует схему 016. Не удаляйте `mcp_membership_losses` и lifecycle receipts: это потеряет защиту rejoin и идемпотентность. После нового edit/rotate/all старый image не является проверенным штатным rollback: он не реализует все принятые права и действия. При проблеме остановите доступ к изменяемой поверхности по согласованному аварийному плану и примените forward fix. Возврат старого backup поверх новых пользовательских данных не является безопасным откатом. Проверка полного backup/restore и runtime rollback относится к общему выпуску #175 и не заявляется выполненной локальной проверкой миграции.
