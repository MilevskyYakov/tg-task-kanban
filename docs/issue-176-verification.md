## Реализация

- `017_chat_directions.sql` сохраняет прежнюю доску и все её ID, добавляя `chat_root_id`, историю chat ID, версию состава, идемпотентный запрос создания и снимок доставки. Личные и pair-доски не объединяются. Общие memberships проецируются на прежние строки с сохранением FK-контракта; удаление членства каскадно отзывает MCP grants. Повторное приглашение не восстанавливает старые grants.
- Общая кнопка (`chat_launch`) выбирает только доски этого чата; одна открывается сразу. Прежние адресные ссылки не выдают права и сохраняют адресацию. Неавторизованный пользователь принимает отдельное приглашение; bootstrap новой группы разрешён только проверенному администратору Telegram.
- Создание проходит под блокировкой корневой доски, с повторной проверкой членства, текущих административных прав и состояния. Перед расширением проверяются версия и явно подтверждённый состав. Старые приглашения отзываются, новая доска открывается пустой, без сообщения в чат. Одинаковый запрос возвращает тот же ID, включая потерянный ответ, параллельные запросы и последующее переименование доски.
- Новый общий состав — управляемый состав Таски, не полная синхронизация с Telegram. Приглашение предупреждает о доступе ко всем направлениям, будущим доскам и истории. Отзыв закрывает UI, прямые ID, API и MCP.
- Дневная и недельная сводки используют настройки корня и независимый выбор досок. Старые время, timezone, дни, статусы и enabled сохраняются. Новая доска не включается автоматически. Пустой выбор не отправляет ничего; исключение из сводки не отзывает доступ.
- При оставшихся отдельных расписаниях создание блокируется, но прежние публикации продолжаются. Администратор явно выбирает общий источник для каждого типа. Версия снимка защищает от устаревшего выбора; уже отправленный legacy отчёт не вызывает вторую общую отправку за ту же дату.
- Длинный отчёт сохраняется в `publication_runs.messages`, делится на нумерованные rich-message части без обрезания задач и фиксирует message IDs/прогресс. Подтверждённый отказ допускает продолжение с неотправленной части. Потерянный ответ, недостоверный receipt или оставшийся `sending` переводят отправку в `uncertain`; автоматического повтора нет. Изменённый состав отчёта не переиспользует старый снимок. Администратор видит неопределённую доставку.
- Freeze/rejoin/migration действуют на весь чат, не оживляют архив и игнорируют старые chat ID. Пустой onboarding-placeholder новой supergroup объединяется с прежним чатом; два уже используемых набора данных автоматически не сливаются. Последний случай требует ручной проверки без удаления истории.
- В форме создания повтор использует сохранённый request ID, в том числе после временного отказа в доступе и перезагрузки. Есть loading/error, устаревшее подтверждение, неизвестный результат, просмотр обычным участником, длинные названия, 200% текста и проверка полной видимости ввода в уменьшенном диалоге.

## Исправления после ревью — до стабилизации UI

Исправлены все три замечания в пределах #176, без изменения миграции и без запуска соседних задач:

1. **Продолжение сводки после переименования.** Состав досок сравнивается независимо от порядка и при повторной доставке, и при сохранении настройки. Переименование доски или перестановка тех же ID больше не отменяют оставшиеся части. Снимок текста сохраняется; реальное изменение состава по-прежнему отменяет частично отправленную сводку, а неопределённый результат доставки не повторяется автоматически.
2. **Черновики прежнего формата.** При восстановлении публикации отсутствующий `included_board_ids` заполняется текущим серверным выбором в `base`, `draft` и сохранённой попытке. Несохранённое время, подтверждение потерянного ответа и реальные конфликты сохраняются. Старый черновик не перезаписывает новый серверный состав досок.
3. **Общая ссылка существующего чата.** Администратору доступна кнопка «Получить общую ссылку» в панели «Доски чата» и `POST /api/boards/:id/chat/link`. Ссылка создаётся для корня чата, выделяется целиком для копирования и не отправляется ботом. Старое приветствие и адресные ссылки остаются неизменными. Проверены административные права, отказ постороннему пользователю без изменения memberships, вход до/после включения нескольких досок и создание ссылки через дочернюю доску. UI-тест получает `chat_launch` через интерфейс/API, а не вставляет его напрямую в БД.

Регрессионные проверки сначала воспроизвели дефекты: API — 2 failures из 4 tests, старые черновики — 3 failures из 3 tests. После исправлений те же проверки прошли. Начальные red-логи сохранены отдельно.

## Стабилизация UI gate

После разрешения продолжить локальный разбор UI исправлены причины оставшихся сбоев, без отключения сценариев, изменения геометрических допусков или добавления retries:

- **Reduced motion.** Универсальный `transition-duration: .01ms` создавал переходы даже у элементов, где их не было. Диагностика CSSOM и `document.getAnimations()` зафиксировала у `body` активные переходы `margin-*` с временем `0`: правило уже задавало `margin: 0`, но вычисленный отступ оставался `8px`, а ширина документа — `328px` при viewport `320px`. Теперь reduced motion использует `transition: none`. `branding.spec.ts` проверяет ширину, нулевой отступ и отсутствие transition без ожидания, скрывающего переполнение.
- **Часы тестов.** Все три места с `clock.install(); clock.pauseAt(new Date())` используют общий `pauseCreationClock` с фиксированным началом и более поздней точкой паузы. Время браузера больше не сравнивается с текущим временем Node. Отдельная локальная проверка воспроизвела прежнюю ошибку при контролируемом сдвиге браузерных часов на 1000 мс, затем проверила паузу и точное срабатывание таймера 300 мс на новой шкале.
- **Поле над клавиатурой.** Трассировка показала, что после двух кадров и корректирующего `scrollBy` браузер мог позднее изменить прокрутку без нового вызова приложения. Общий `useTaskKeyboardViewport` теперь повторно проверяет поле по `scrollend`, пока последним намерением был ввод/фокус/resize. Колесо и touchmove отменяют эту проверку до следующего ввода, поэтому намеренная ручная прокрутка не возвращается назад. Сохранены прежние проверки масштаба, типа поля, диалогов и два кадра для начального изменения высоты. Удаление обработчиков входит в cleanup.

В keyboard-сценарий добавлены детерминированные проверки: завершение ручной прокрутки оставляет страницу на месте, а завершение поздней браузерной прокрутки после ввода возвращает поле в видимую область. Исходный сценарий сохранён. Проверены обе ширины 320/390 px, обычное и reduced motion; 40 целевых запусков с четырьмя повторениями прошли. `npm run test` (78 тестов), `lint`, `typecheck` и `build` прошли на исправленном коде.

Полный `npm run test:visual` завершился с кодом 0: **291/291 PASS**, без исключений сценариев и retries. Лог: `ui-stability-visual-full.log`. Диагностические и финальные логи имеют префикс `ui-stability-` в `artifacts/evidence/issue-176-runtime/`. Снимки ошибки входа и ввода при уменьшенном viewport осмотрены. Временная трассировка удалена из тестов. Хэши API-исходников совпадают с этапом ревью, поэтому результаты неизменённых public-entry/cutover сохранены без повторного запуска. Собственный PostgreSQL и временные web-серверы остановлены.

Актуальный машиночитаемый снимок: `artifacts/evidence/issue-176-ui-verification.json`. Новые измерения input performance сохранены в `ui-stability-input-perf.jsonl`; исторический общий JSONL восстановлен без изменений.

Это проверка локального Chrome, не физической клавиатуры Telegram. Дополнительная коррекция использует нативный `scrollend`; на WebView без этого события сохраняется прежний двухкадровый путь. Реальная iOS/Android-приёмка и согласованный выпуск остаются отдельными gates.

## Миграция и восстановление

`chat-migration.test.ts` создаёт отдельную БД со схемой до 017, существующими пользователем, доской, проектом, задачей, адресной ссылкой и разными расписаниями. Реальный migration CLI сохраняет строки/ID и независимые timezones. Старые `sending` и `pending` с уже начатой попыткой становятся `uncertain`, а не автоматически отправляются снова. После создания направления повтор CLI — no-op: отдельные расписания дочерних досок не возникают. Искусственная SQL-ошибка проверяет rollback, выход процесса без зависания, освобождение соединения и успешный повтор.

При явном объединении расписаний оставшийся legacy `sending` также становится `uncertain` и остаётся виден в общих настройках. Очередь без уже удалённого расписания классифицируется, а не зацикливает worker; отдельная API/DB-проверка подтверждает отсутствие повторной отправки и бесконечного цикла.

**Откат к runtime до 017 несовместим сразу после миграции**, а не только после создания второй доски: прежний `ON CONFLICT` больше не соответствует частичному уникальному индексу. Сохранение чтения отдельных личных данных старым API не доказывает работоспособность группового входа, отправителя или прав.

До отдельно разрешённого выпуска необходимо:

1. Сверить release SHA, версии PostgreSQL и все миграции объединённого пакета; проверить согласованность #178/#180/#182.
2. Получить свежий backup и выполнить restore-smoke в отдельной БД целевой версии. Локальный тест на PostgreSQL 14 не заменяет production PostgreSQL 17.
3. Остановить прежний отправитель до применения 017, классифицировать in-flight отправки; не запускать два runtime/scheduler и не сбрасывать delivery receipts или очередь Telegram.
4. Применить миграции новым CLI и запустить только совместимый код. Проверить прежние ID, адресный/общий вход, явное приглашение, отзыв API/MCP, расписания, неизвестные исходы и отсутствие двойных публикаций.
5. При регрессии сохранить текущую БД и новые записи. Использовать совместимый forward-fix либо отдельно согласованный recovery-план. Не удалять новые направления и не восстанавливать старый dump поверх живых данных ради запуска старого image.
6. Пройти отдельно разрешённую реальную Telegram/device-приёмку и общий release gate. Настоящая отправка длинной сводки, физические клавиатуры iOS/Android и транспортные условия production этим пакетом не доказаны.
