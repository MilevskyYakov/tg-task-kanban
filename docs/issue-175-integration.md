Разрешён смысловой конфликт #176/#180: старый сценарий #180 допускал присоединение по одному Telegram-membership. Более поздняя принятая модель #176 требует явного состава Таски. Адресные `open_`/`task_` проверяют уже выданный доступ; launch существующей активной группы тоже не добавляет постороннего. Bootstrap администратора draft-группы и явное принятие приглашения сохранены. Политика не ослаблена ради старого теста.

Сохранена интеграционная поправка готовности #179/#180: восстановление обычного выбранного board при failed link и hydration фильтров не должны перекрывать адресный вход. В browser fixtures учтено, что новая неоценённая задача по принятому #177 находится в свёрнутой группе «Не разобрано»; тест сначала раскрывает группу, а не меняет продуктовую модель.

В `chat-directions.test.ts` добавлен сквозной сценарий: создание направления, selected/all MCP, nullable-оценки задач, per-board filters, настоящий multipart upload/readback, адресный вход, отказ постороннему, удаление membership и последующая потеря доступа MCP/вложению/ссылке. Используются только синтетические пользователи и отдельная локальная БД.

Исправлен standalone `mcp-migration.ts`: legacy-задача создаётся SQL старой схемы, а не новым runtime, требующим `chat_root_id`. Проверяется настоящий migration runner, сохранность ключа/grants/содержимого задачи/receipts, ровно одно техническое увеличение task revision при assessment backfill и отсутствие повторных изменений. После миграции прежний ключ проверен настоящим HTTP/SDK.

Первый полный browser-прогон выявил потерю прокрутки при возврате из создания: короткий loading-placeholder перезаписывал снимок списка. Общая точка сохранения/восстановления теперь заморожена до `taskLoadState === 'ready'`; восстановление отменяется при уходе с экрана. Исправление покрыто существующими строгими scroll/filter-сценариями, без увеличения допуска. В legacy settings fixture завершение начального refresh ожидается до записи искусственного старого черновика, чтобы тест сам не стёр его незавершённым чтением. Полный повторный прогон выполняется после этих исправлений на замороженных исходниках.

## Миграции и проверки

Имена `016_mcp_lifecycle.sql` и `016_task_assessment.sql` различны и не переименованы. Runner сортирует полные имена; затем применяется `017_chat_directions.sql`. Он ведёт `schema_migrations` под advisory lock: повторный штатный запуск не восстанавливает старые per-board schedules после объединения чата. Для production с прежним runner первая установка журнала повторно применяет исторические идемпотентные SQL; legacy fixture и повторный запуск проверяются отдельно.

Проверочный контур: существующий локальный PostgreSQL, только новые `tasca_issue175_*` / `tasca_rehearsal_issue175*` БД, Chrome через Playwright с временным изолированным профилем. Личный браузер, production-БД, реальный bot token и действующие MCP-ключи не использовались. Telegram API в локальных сценариях замокан. Это не Telegram/device-приёмка.

После продолжения подготовки Docker Desktop запущен; исходный `Dockerfile` собран для `linux/amd64` без изменений продуктового кода. Docker Hub из daemon недоступен по IPv6, поэтому базовые `node:22-alpine` и `postgres:17-alpine` загружены из официального публичного mirror ECR. Digest индексов и выбранных amd64 manifests сверены с Docker Hub и совпали; настройки сети и VPN не менялись.

Docker gate пройден на disposable PostgreSQL 17 Alpine: все миграции и повторный запуск, штатный `CMD` под пользователем `node`, production cookie flags, подписанный синтетический вход, задача с оценками, upload/readback изображения и отказ без авторизации, настоящий MCP SDK, сохранность сессии/задачи/файла/прежнего MCP-ключа после restart. Проверены байты собранных JS/CSS и SHA-256 обеих Telegram-обложек в образе. Проверки HTTP выполняются внутри изолированного контейнера; попытка доступа через published port в `--internal` сети не дала readiness. Публичный ingress/TLS и реальные устройства этим не проверены. Контейнеры, временная БД и сеть удалены с readback; Telegram и production не затрагивались.

## Остановка и восстановление

До миграции можно отменить окно, оставив прежний runtime и БД. После `017_chat_directions.sql` возврат образа `3a358f4` **не является рабочим rollback**: старый `ON CONFLICT` для chat board несовместим с новым индексом; старый код не реализует общий membership и новый MCP lifecycle. Это подтверждено локальным cutover-тестом.

При регрессии после миграции остановить дальнейшие внешние записи и sender в согласованном порядке, сохранить текущую БД/receipts, выполнить совместимый forward fix и повторную проверку. Для независимого аварийного восстановления нужен отдельно проверенный recovery-пакет. Не удалять направления, журналы MCP или записи после переключения ради отката; не восстанавливать старый dump поверх текущей БД. Готовность аварийного оператора и приемлемого плана остановки остаётся release gate.
