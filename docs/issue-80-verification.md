## Реализованное поведение

- `/start` в личном чате объясняет назначение и предлагает «Личные задачи», «Доска на двоих», «Доска для группы». `/help` и кнопка «Помощь» в настройках повторно открывают инструкции. Обычный запуск без `start_param` не включает обязательное приветствие и сохраняет обычный контекст доски.
- Явные entry-параметры `personal`, `pair`, `group`, `help` открывают соответствующий путь. Существующие `pair_…`, board/invite и task deep links не заменены общим выбором. Недействительная ссылка показывает отдельный отказ без данных доски, временная ошибка позволяет повторить тот же вход.
- Новая групповая доска получает одно multipart `sendPhoto`: исходный `artifacts/ux/assets/group-welcome.png`, HTML-подпись с экранированным названием и одна кнопка «Открыть задачи». Изображение проверяется тестом по SHA-256 принятого asset. Dockerfile включает этот же файл без отдельной копии в исходниках. Приложение не закрепляет и не редактирует сообщение.
- Первичный вход по кнопке проверяет текущие Telegram-admin права на сервере. Администратор видит настройку, участник — ожидание и проверку готовности. После активации оба открывают задачи через ту же ссылку. Повтор POST активации не переименовывает уже активную доску и не размораживает удалённого бота.
- При потерянном ответе активации форма сохраняется; повтор сначала читает состояние сервера. Успешно активированная доска не откатывается из-за ошибки отправки сообщения или потери HTTP-ответа.
- В пустой активной доске доступны первая задача и вставка списка. Существующие права, бэклог, парный доступ и task details переиспользованы.
- Замороженная доска не принимает новых участников по ссылке; уже вступивший видит объяснение. Возврат бота восстанавливает прежнее состояние и ссылку без нового сообщения. Порядок membership events сравнивается по Telegram `date`, затем `update_id`: случайный новый ID после длительного простоя не блокирует восстановление.

## Доставка и диагностика

Миграция `011_bot_entry.sql` добавляет только служебное состояние. У существующих досок нет новой welcome-записи; восстановление такой доски не инициирует миграцию закрепа или отправку нового сообщения. Старые launch-ссылки не отзываются при повторном подключении.

`telegram_entry_deliveries` хранит один ключ новой доски либо личной команды, статус, число попыток, безопасный код ошибки и подтверждённый `message_id`. Ключ команды — SHA-256 пары chat/message ID: повторный `update_id` после простоя не подавляет новую команду. Текст сообщения, bot token, launch token и Telegram payload в таблицу не записываются. Новые launch-токены хранятся в `board_links` только как hash. Доступ к самой БД остаётся административным; ключи команд и message IDs не предназначены для публичного evidence.

- `pending` / `failed`: попытку атомарно забирает только один обработчик. Подготовка файла/запроса до отправки может быть повторена. Явный отказ Telegram 4xx, включая 429, сохраняется как `telegram_<code>` и возвращает HTTP 503 для повторной доставки webhook.
- `sending`: параллельный обработчик не отправляет второе сообщение. Если процесс прервался, при следующем обращении запись старше двух минут становится `uncertain` с кодом `interrupted`.
- `sent`: только после ответа Telegram с `message_id` и сохранения результата в БД. Повтор не отправляет сообщение и не меняет успешную ссылку.
- `uncertain`: потеря сетевого ответа, неоднозначный 5xx, неполный ответ или ошибка сохранения результата после отправки. Возвращается HTTP 200 с `ok: false, delivery: "uncertain"`, чтобы остановить автоматические повторы; это подтверждение обработки webhook, не успешной отправки. Лог: `Bot entry delivery unconfirmed; automatic resend blocked`.

Ограничение намеренное: [Bot API](https://core.telegram.org/bots/api#sendphoto) не предоставляет send-idempotency key или поиска отправленного сообщения по нашему ключу. Автоматическое восстановление после неопределённого результата могло бы создать скрытый дубль. Нельзя обещать exactly-once при потере ответа. Нужна ручная проверка конкретного тестового чата: если сообщение есть, сохранить факт доставки; если его отсутствие подтверждено — отдельно разрешить одну повторную попытку. Нельзя вслепую переводить все `uncertain` в `pending`, повторно подключать все группы или запускать рассылку. Команда обновления закрепа не добавлена.

Безопасная сводка для оператора, без чатов, пользователей, токенов и текстов:

```sql
SELECT status, error_code, count(*)
FROM telegram_entry_deliveries
GROUP BY status, error_code;
```

## Проверки

- `npm run test`: 32 unit + 12 API/DB tests, без ошибок и пропусков.
- `npm run test:visual`: 49 Playwright tests, успешно; основные сценарии на 390×844 и 320×844. Дополнительный regression check проверяет выход из setup сохранённой замороженной доски к настройкам и помощи без изменения обычного выбора.
- `npm run lint`, `npm run typecheck`, `npm run build`, `git diff --check`: успешно. `lint` — alias typecheck.
- `npm ci --include=dev` сообщил о двух прежних dependency findings: moderate и high. Lockfile не менялся; общий security gate не заявляется пройденным.

`apps/api/test/chat-board.test.ts` включён в существующий root gate. Проверены фото/подпись/кнопка, hash asset, параллельные и последовательные повторы, ошибки и uncertain, прерванная попытка, постоянный токен, setup/admin/member, успешная активация при последующем retry доставки, freeze/restore, старые доски без рассылки и `/start`/`/help` только в личном чате.

`apps/web/visual/entry.spec.ts` автоматически включён в `test:visual`. Две синтетические браузерные сессии используют настоящие Fastify handlers и PostgreSQL: участник ждёт, администратор активирует с потерей ответа, повтор читает успешное состояние, создаётся первая задача, участник видит её в бэклоге, повторный вход открывает ту же доску. Проверены task deep link и возврат, freeze/restore, обычная личная доска после группового запуска, помощь и boot при недоступном storage. Проверены фокус заголовка, отсутствие ошибок JS, overflow и 200% текст в инструкции. Telegram auth и Bot API в harness mocked; это не реальная доставка Telegram.

Композиция вручную сверена с принятыми group connect и pair entry exports: белый фон, заголовок, шаги, поле названия, ожидание, ошибка и нижние действия. Это не pixel-diff. Воспроизводимые PNG находятся в игнорируемом `artifacts/visual-evidence/entry-*.png`; формат настоящего сообщения должен быть проверен в Telegram, а не на имитации чата.

## Непройденный Telegram / #83 checklist

Требуются отдельно разрешённый тестовый bot/runtime, изолированный чат, реальный администратор и участник. Не использовать production-группы для проверки.

- [ ] iOS и Android: `/start`, все три пути и повторный `/help`; самостоятельный выбор сценария без устных инструкций.
- [ ] Добавление бота: Telegram действительно принимает multipart PNG, подпись и inline-кнопку как одно сообщение. Проверить обрезанное представление закрепа.
- [ ] Пользователь закрепляет сообщение. Участник видит ожидание; администратор запускает доску; оба возвращаются через ту же кнопку, без нового сообщения и общего onboarding.
- [ ] Команда создаёт первую задачу, второй участник видит её и берёт себе. Task deep link и возврат работают в реальном WebView.
- [ ] В тестовом контуре проверить явный отказ отправки и безопасный повтор; отдельно — неопределённый результат без автоматического дубля. Зафиксировать обезличенные состояния БД и фактический результат в чате.
- [ ] Удаление/возврат бота, ограничения прав, неверная/отозванная ссылка, недоступное хранилище и сеть на устройствах.
- [ ] Проверить возврат в группу, размер текста, экранный диктор, safe areas и клавиатуру. Mocked `openTelegramLink` / `close` не доказывают работу на устройстве.

До этих проверок не заявлять Telegram smoke, самостоятельную продуктовую приёмку или release-ready. Следующий продуктовый этап программы — #82, без автоматического запуска. #83 и #75 остаются открытыми; production rollout требует отдельного разрешения.
