## 1. Минимальная архитектура

- Один MCP endpoint `/mcp` в существующем Fastify API, на том же origin. Новый HTTP-сервис, Express-приложение, OAuth-сервер, Redis и отдельный deployment не нужны.
- Streamable HTTP с JSON-ответами, без серверных MCP-сессий, SSE-стримов, resources, prompts, sampling и фоновых MCP tasks.
- Первая совместимая протокольная база — `2025-11-25` с обычным `initialize`. Это намеренно не обещание поддержки новой редакции `2026-07-28` и `server/discover`.
- SDK-база: `@modelcontextprotocol/sdk@1.30.0`, зафиксирована в manifest/lockfile. Настоящий SDK Client прошёл loopback HTTP smoke; документация Hermes подтверждает подходящий legacy handshake и Streamable HTTP. Это не заменяет пользовательский Hermes smoke.
- Использовать `McpServer` из `@modelcontextprotocol/sdk/server/mcp.js` и `StreamableHTTPServerTransport` из `@modelcontextprotocol/sdk/server/streamableHttp.js`. Настройки: `sessionIdGenerator: undefined`, `enableJsonResponse: true`. Проверить эти imports/options на установленной зафиксированной версии при реализации, до широкого изменения кода.
- Zod объявлен прямой зависимостью `4.3.6`, версии зафиксированы lockfile. Для входных tool schemas используется `io: 'input'`, чтобы default-поля не становились обязательными для клиента. Финальный `npm audit --omit=dev` не обнаружил уязвимостей; это результат конкретного прогона, не бессрочная гарантия.
- Fastify передаёт уже разобранный body и свои Node request/response объекты в SDK. Перед передачей response вызвать `reply.hijack()`; закрытие transport/server привязать к завершению response, без второй отправки через Fastify. Проверить lifespan на disconnect/error. Не переносить Express из примера как новую серверную архитектуру.
- Новый server/transport создаётся на запрос. Контекст пользователя связан с проверенным ключом этого запроса; никакого общего изменяемого `currentUser` или кэшированной авторизации между клиентами.
- MCP-адаптер вызывает общий task service. Telegram REST и MCP используют одни проверки полей, прав, сроков, блокеров, checklist confirmation, audit и побочных эффектов. Не делать внутренние HTTP-запросы с поддельной cookie.

### HTTP-контракт `/mcp`

| Запрос | Поведение |
|---|---|
| POST с действующим Bearer | Проверка доступа и передача JSON-RPC в SDK; JSON-ответ для request, штатный 202 без body для принятой notification |
| GET с действующим Bearer | 405, `Allow: POST`, `Content-Type: application/json`; отдельного SSE-стрима нет |
| HEAD с действующим Bearer | 405 с теми же metadata headers, без body; не отдавать HTML SPA |
| DELETE с действующим Bearer | 405: серверной MCP-сессии для удаления нет; это не отзыв ключа |
| Нет ключа, неверный или отозванный ключ | 401 с одинаковым безопасным сообщением и `WWW-Authenticate: Bearer realm="task-kanban-mcp"` |
| Неподдерживаемый protocol header, неверный JSON-RPC | Ошибка HTTP/JSON-RPC согласно SDK и согласованной редакции протокола |
| Чужой Origin | 403 до бизнес-операции; не отражать Origin произвольно |
| Перегрузка/ограничение запросов | 429 с `Retry-After`; запись не начинается |

Bearer проверяется для каждого метода и вызова. Session cookie и Telegram initData не авторизуют `/mcp`; MCP-ключ не авторизует обычный `/api/*`. Query string с токеном запрещён. `/mcp` не попадает в SPA fallback и не перенаправляется на другой origin.

Origin отсутствует у нативного клиента — это допустимо при действующем Bearer. Присутствующий Origin должен точно совпасть с разрешённым origin приложения; `null` и чужие origins запрещены. Проверять Host по конфигурации сервера, не доверять произвольным forwarded headers. Production — HTTPS с проверкой TLS; локальный smoke — loopback и синтетические ключи. CORS `*` с credentials не включать.

Ручной Bearer — выбранный app-specific механизм доступа. Не публиковать фиктивные OAuth discovery endpoints и не выдавать его за реализацию полного MCP OAuth-контракта. Клиенты, требующие исключительно OAuth, не поддерживаются первой версией.

## 2. Подключения и жизненный цикл ключа

### Модель

Подключение содержит `id`, `userId`, `name`, `mode`, `createdAt`, `revokedAt`, `createRequestId`, `keyHash` и явные grants на `boardId`. `mode` — `read` либо `write`; `write` включает чтение. Название — 1–80 символов после trim. Режим один на подключение, не отдельная матрица по доскам.

- Пользователь выбирает хотя бы одну свою доску. По умолчанию ничего не выбрано и установлен режим `read`.
- Разрешения после создания неизменяемы. Для другого состава досок/режима — отозвать и создать новое подключение. Это минимальная первая версия, без in-place расширения прав.
- Ключ формируется CSPRNG: `ktk_mcp_` + base64url от `randomBytes(32)`, без padding. Проверять точную структуру до lookup, не исправлять/нормализовать произвольный вход. Сервер хранит SHA-256 полного ключа, не сам ключ. Высокоэнтропийному случайному ключу не нужен парольный KDF.
- Срока действия и плановой ротации нет. Компромисс принят владельцем: при утечке доступ сохраняется до отзыва.
- Полный ключ возвращается только в успешном первом ответе создания. Хранится в памяти открытого экрана до выхода, не в localStorage/sessionStorage, URL, analytics, crash reports или Git. Перезагрузка и уход со страницы удаляют его из памяти.
- Отозванное подключение остаётся видимым как отозванное. Его ключ никогда не оживает повторным созданием, возвратом membership, перезапуском API или повтором старого запроса.
- При потере membership grant этой доски инвалидируется в той же транзакции удаления membership. Повторное вступление не восстанавливает старый grant: для этой доски требуется новое подключение. Не хранить/показывать MCP-клиенту названия досок, к которым доступ уже потерян. UI владельца подключения показывает нейтральное «Доступ к доске потерян» без исторического названия.
- Архив/заморозка не равны отзыву membership. Чтение остаётся в пределах существующей модели, запись разрешена только в `active`. Разархивация не добавляет новые grants.

### Управление — только из авторизованного приложения

Предлагаемые endpoints:

| Endpoint | Вход | Результат |
|---|---|---|
| `GET /api/mcp-connections` | `limit`, `cursor` | Только собственные подключения: id/name/mode/status/createdAt, доступные выбранные доски и число потерянных grants; без ключа/хеша |
| `POST /api/mcp-connections` | `{requestId, name, boardIds, mode}` | 201 `{connection, key}` только при первом создании |
| `GET /api/mcp-connections/:id` | UUID | Собственная конфигурация без секрета; чужой/несуществующий id одинаково 404 |
| `DELETE /api/mcp-connections/:id` | UUID | 200 `{id, revoked: true}`; повтор отзыва собственного подключения возвращает тот же результат |

Создание принимает только перечисленные поля. `userId`, `revokedAt`, `keyHash`, expiry и произвольные права из клиента не принимаются. Владелец определяется сессией, grants валидируются по membership сервером, вся операция атомарна. Board IDs дедуплицируются; отсутствующие/чужие доски дают общий отказ без частичного создания.

Для mutating management endpoints требуются действующая HttpOnly-сессия, точный Origin приложения и JSON; SameSite cookie не единственная защита от CSRF. MCP Bearer вместо session не подходит. GET также не открывается cross-origin. Ответы управления и `/mcp` имеют `Cache-Control: no-store`; страницы выдачи ключа — `Referrer-Policy: no-referrer`. Не размещать на них сторонние виджеты.

### Потеря ответа при создании ключа

Однократный показ не совмещается с повторной выдачей plaintext из hash-only хранилища. Это решается явно, без скрытого хранения секрета:

1. UI создаёт `requestId` до отправки и удерживает его с формой в памяти.
2. Уникальность `(userId, createRequestId)` защищает от второго подключения при повторе. Нормализованное содержимое сохраняется как fingerprint.
3. Повтор того же запроса после уже совершённого создания возвращает 409 `KEY_ALREADY_ISSUED` и безопасную metadata своего подключения, но не ключ. Другой payload с тем же id — 409 `REQUEST_CONFLICT`.
4. После timeout UI не создаёт новый requestId автоматически. Показывает неопределённый результат и предлагает «Проверить результат» с прежним requestId. Если исходный запрос не был committed, этот повтор может успешно завершить одно создание; если был — вернёт `KEY_ALREADY_ISSUED`.
5. Если ключ недоступен, UI предлагает отозвать это подключение. Только после подтверждённого отзыва доступна новая форма с новым requestId. Не оставлять скрытый активный ключ ради автоматического retry.
6. Уход с неизвестным результатом не превращает его в success. Позже собственное подключение видно в списке; без исходного секрета доступны просмотр прав и отзыв.

### Отзыв и запрос в полёте

Отзыв — барьер новых операций, не отмена уже committed задач и не удаление данных, уже прочитанных клиентом.

Для вызова, работающего с данными: DB-транзакция удерживает shared lock записи подключения, повторно проверяет `revokedAt`, затем проверяет grants и membership. Для записи далее берётся существующий advisory lock доски и row locks на доску/membership/task. Все вызовы используют один и тот же порядок блокировок. Отзыв берёт конфликтующий lock записи подключения и фиксирует `revokedAt`.

Операция, уже удерживающая разрешающий lock, может завершиться перед подтверждением отзыва. После успешного ответа отзыва ни одна новая операция с этим ключом не может начать/закоммитить запись. Ответ ранее завершённого чтения может ещё находиться в сети; обещать удаление данных из контекста модели нельзя. Lock timeout не выдаётся за успешный отзыв; UI сохраняет статус «Не удалось подтвердить отзыв».

Membership/grant и проверка mutation должны находиться в той же DB-транзакции. Нельзя проверить grant снаружи и вызвать `createTask` на другом connection, оставив окно обхода. Минимально выделить transaction-aware тела общих task операций с сохранением внешних REST wrappers; не вводить новый универсальный repository/service framework.

## 3. Точный набор MCP-инструментов

Все schemas строгие: неизвестные поля запрещены, UUID и decimal user IDs проверяются до SQL, bigint IDs передаются строками. Actor identity не является параметром ни одного инструмента. Значения `self` разрешаются только из проверенного подключения. Все данные задач считаются недоверенным содержимым, не инструкциями сервера.

| Инструмент | Вход | Выход и доступ |
|---|---|---|
| `list_boards` | `{limit?, cursor?}` | `{user: {id, firstName}, mode, items: [{id, name, type, status}], nextCursor}`. Только grants ∩ текущие membership, без Telegram chat IDs |
| `list_projects` | `{boardId, query?, limit?, cursor?}` | `{items: [{id, name}], nextCursor}`. Только неархивные проекты выбранной доски |
| `list_members` | `{boardId, query?, limit?, cursor?}` | `{items: [{id, firstName, username}], nextCursor}`. Только текущие участники этой доски, без Telegram IDs |
| `list_tasks` | `{boardId, query?, projectId?, assignee?, statuses?, backlog?, archived?, limit?, cursor?}` | Краткие задачи разрешённой доски; `assignee` — decimal user ID, `self` или `unassigned` |
| `get_task` | `{boardId, taskId, descriptionOffset?, descriptionLimit?, version?}` | Полная доступная task metadata и порция описания; без comments/files/history payload |
| `create_task` | `{boardId, requestId, title, description?, projectId?, assigneeUserId?, priority?, deadline?, status?, blocker?}` | `{task, receipt, replayed, warnings}`; требуется `write` и обычные права создания |
| `update_task` | `{boardId, taskId, requestId, expectedVersion, changes, confirmIncompleteChecklist?}` | `{task, receipt, replayed, warnings}`; требуется `write` и обычные права изменения |

`changes` содержит только `assigneeUserId`, `deadline`, `status`, `blocker`; хотя бы одно поле обязательно. Изменение title/description/project/priority существующей задачи не входит в принятую первую поверхность. `create_task` поддерживает эти обычные поля создания. На экземпляре повторяющейся задачи изменение применяется только к нему, не к будущей серии.

Не добавлять инструменты удаления/архивации/восстановления, администрирования, создания проектов, приглашений, файлов, comments, checklist writes, публикаций, recurrence management и batch/import. Отдельный `claim_task` не входит в эту версию: назначение следует текущим правилам `updateTask`, а не обходу прав обычного участника. Действующий UI «Взять себе» сохраняется.

`tools/list` для read-only показывает только читающие инструменты. Прямой вызов имени write-инструмента всё равно проверяется сервером и даёт `READ_ONLY`, не выполняет операцию. При регистрации handlers не оставлять скрытый обход. Annotations чтения: `readOnlyHint: true`, `destructiveHint: false`, `openWorldHint: false`; записи: `readOnlyHint: false`, консервативно `destructiveHint: true`, `idempotentHint: true` только вместе с обязательным requestId. Это hints клиенту, не authorization.

### Task DTO

Краткая задача: `id`, `boardId`, `projectId`, `title`, `creatorUserId`, `assigneeUserId`, `status`, `priority`, `deadline`, `overdue`, `archived`, `version`. `get_task` добавляет `description`, `descriptionOffset`, `nextDescriptionOffset`, `blocker`, `checklist: {total, completed}`, `recurring`, `createdAt`, `updatedAt`.

Не отдавать `SELECT *`, `create_request_hash`, внутренние notification rows, Telegram identifiers или ключи. Ссылки в описании возвращаются текстом; сервер не следует по ним. File IDs/URL вложений не включаются. Audit записывается обычному actor; клиент не получает всю audit history как побочный результат чтения задачи.

`version` — непрозрачная для клиента строка ревизии задачи. Предлагаемая реализация: монотонная DB-ревизия с trigger при любом UPDATE задачи, в том числе UI, recurrence и удалении assignee после membership loss. На миграции существующим задачам присваивается начальная ревизия без изменения сроков/статусов. Не строить optimistic concurrency на миллисекундном JS Date, если PostgreSQL хранит более точное время.

### Поиск и пагинация

- У списка задач обязательна одна выбранная доска. Агент может пройти свои доски из `list_boards`; общего неограниченного dump всех задач нет.
- `query`: trim, до 200 символов; обычный регистронезависимый поиск подстроки в title/description задач или названиях справочника. SQL параметризован; `%`, `_` и escape символ экранируются как литералы. Нет regex, произвольного ORDER BY и новой поисковой инфраструктуры.
- `limit`: по умолчанию 25, максимум 100, положительное целое. Cursor ограничен по длине и проверяется по структуре. Все списки имеют `nextCursor: string | null`; totals не выдаются, если не вычислены.
- Задачи сортируются по `(createdAt DESC, id DESC)`, keyset cursor хранит эту границу и fingerprint фильтров, board и connection. Board/project/member списки — по стабильному id. Cursor не является разрешением: все права повторно проверяются перед каждой страницей. Подмена границы не открывает недоступные записи.
- Изменение фильтров с прежним cursor — `INVALID_CURSOR`. Пустая разрешённая доска даёт `items: []`; чужая или невыбранная — `NOT_FOUND`, не маскируется пустой страницей.
- `statuses` по умолчанию включает активные статусы без `done`; завершённые запрашиваются явно. `archived` по умолчанию `false`, `true` означает только архивные задачи. `get_task` разрешает чтение конкретной архивной задачи, но не изменение.
- `backlog: true` означает неархивные `todo` без исполнителя; конфликтующие фильтры отклоняются, не меняются молча.
- Списки живые, не snapshot всей доски. Изменения статуса/фильтра во время обхода могут изменить выдачу; повторить поиск для нового актуального результата. Keyset предотвращает offset-дубли от вставок, но не обещает транзакционный snapshot между запросами.
- Описание возвращается `get_task` порциями: offset по Unicode code points, limit по умолчанию/максимум 8000. `nextDescriptionOffset: null` обозначает конец, не тихое обрезание. На второй и последующих порциях обязателен `version`, полученный первой; изменившаяся задача даёт `VERSION_CONFLICT`. Offset вне строки отклоняется.

### Поля создания, срока и блокера

- `title`: trim, 1–200 символов. Новое описание — максимум 8000 code points, plain text. Старые длинные описания не обрезаются в БД и читаются порциями.
- `priority`: `normal` по умолчанию либо `urgent`. `status`: `todo` по умолчанию либо `in_progress`, `waiting`, `done`.
- `assigneeUserId` и `projectId`: ID текущего участника/активного проекта той же доски либо null. Нельзя назначить по неоднозначному имени без выбора id.
- `deadline`: `{kind: "none"}`, `{kind: "date", date: "YYYY-MM-DD", timezone: "IANA zone"}` либо `{kind: "datetime", at: "RFC3339 timestamp with explicit offset"}`. У create отсутствие означает `none`; у update отсутствие означает не менять, `none` — очистить. Дата и часовой пояс строго валидируются, не берутся с сервера и не угадываются. Date-only означает весь календарный день; точные старые timestamps не переинтерпретируются.
- `blocker`: `{kind: "task", taskId}` либо `{kind: "external", reason, checkAt?}`. Причина — 1–1000 символов после trim, `checkAt` — timestamp с offset. Начальный `waiting` требует ровно одно основание. При update уже ожидающей задачи можно сохранить действующее основание; переход в `waiting` без него запрещён. Другие статусы очищают блокер по общей модели; передача противоречивого blocker с non-waiting отклоняется.
- Связанная задача — активная, той же доски, не текущая задача; циклы запрещены общим правилом. Назначение вместе с `done` не обходит проверку прав завершения по существующей матрице.

### Checklist и уведомления

`update_task` с переходом в `done` проверяет незавершённый checklist в общей транзакции под board lock. Без явного `confirmIncompleteChecklist: true` возвращает `CHECKLIST_CONFIRMATION_REQUIRED` с count. Клиент должен спросить пользователя, а не выставлять флаг автоматически. Сервер может проверить флаг и состояние, но не доказать наличие человеческого ответа внутри стороннего клиента.

После подтверждения отправляется новый intent с новым requestId и актуальной `expectedVersion`; прежний запрос не превращается молча в другую запись. Конкурентные checklist edits должны брать тот же board lock, что completion. Перенести эту проверку из отдельного HTTP-only precheck в общий mutation path, сохранив REST UX.

MCP не открывает `notifyAssignee`: назначение не отправляет дополнительное личное сообщение по умолчанию. Действующие системные эффекты завершения — снятие блокеров и уведомление разблокированных исполнителей — сохраняются. Это не инструмент произвольной публикации. Не отключать существующие групповые расписания как побочный эффект MCP: они продолжают читать актуальные задачи обычным способом.

Notification intent создаётся в одной транзакции с записью задачи. Доставка после commit использует существующий claim/status механизм. Её ошибка возвращается warning «Задача сохранена, но уведомление не доставлено», не общим rollback записи. Повтор запроса не создаёт новые intents и не запускает неизвестную доставку повторно. Exactly-once доставку Telegram API не обещать.

## 4. Повтор записи, конфликты, аудит

Обязательный `requestId` — UUID клиента для одного намерения. Потеря сети требует того же id и содержимого; новая самостоятельная операция, в том числе сознательно одинаковая задача, получает новый id. JSON-RPC id не является idempotency key.

Нужна durable receipt записи с уникальностью `(connectionId, requestId)`: operation, boardId, taskId, fingerprint нормализованного payload, committed revision, минимальный результат и warning/notification references. Не хранить там secret или дополнительную копию всего текста задач. Receipts живут всё время действия подключения; отзыв делает повтор с ключом недоступным. Не вводить короткое TTL, после которого старый повтор вдруг становится новой задачей.

Алгоритм одной DB-транзакции:

1. Проверить ключ и взять shared connection lock; проверить `write`, актуальный grant и membership.
2. Сериализовать одинаковый requestId и взять существующий board lock в едином порядке для всех MCP writes. Повторно проверить активность доски.
3. Найти receipt. Тот же fingerprint и operation — вернуть подтверждённый receipt без новой записи. Другой payload — `REQUEST_CONFLICT`. Перед возвратом receipt вновь проверить доступ; отзыв/membership loss не обходятся через кэш.
4. Для новой update-операции заблокировать задачу, проверить `expectedVersion`, task permissions и checklist/blocker. Несовпадение версии — `VERSION_CONFLICT`, без перезаписи чужого изменения.
5. Выполнить общую mutation, audit и notification intents. Записать receipt в той же транзакции. Commit один на всё.
6. После commit вернуть спроецированную задачу и receipt. Повтор возвращает текущую доступную задачу вместе с исходной committed revision и `replayed: true`; если задача позже архивирована, вернуть безопасную доступную архивную проекцию, не выполнять запись снова.

Существующий `createTask.requestId` переиспользуется внутри этой схемы, а не заменяется дедупликацией по названию. Его область уникальности `(board, creator, requestId)` отличается от connection receipt: внутренний create request UUID связывается с receipt, чтобы два подключения одного пользователя с совпавшими внешними requestId не мешали друг другу.

Validation/access/conflict errors до commit не записываются как успешные receipts. Deadlock/timeout/DB exception приводит к rollback. Если клиент не получил ответ и не знает commit outcome, он повторяет тот же запрос. Никакого автоматического «попробовать с новым requestId».

Audit сохраняет правильного `actor_user_id`. Для MCP события дополнительно связываются с connectionId/requestId, но не с секретом и не с выдуманным отдельным пользователем-ботом. Existing task timeline продолжает показывать реального пользователя; не открывать agent-wide audit dump.

## 5. Контракт ошибок

Успешный tool result содержит `structuredContent: {ok: true, ...}` и эквивалентное JSON-представление в text content. Бизнес-ошибка — `isError: true`, `structuredContent: {ok: false, error: {code, message, retryable, ...safeDetails}}` и то же безопасное содержание текстом. Output schema допускает обе ветви. Protocol errors и неизвестный method остаются JSON-RPC errors SDK; не смешивать их с подтверждённой записью.

| Код | Значение | Следующее действие |
|---|---|---|
| `AUTH_REQUIRED` | Ключ отсутствует/неверен/отозван, HTTP 401 | Остановить обращения; открыть Подключения. Без автоматического OAuth |
| `READ_ONLY` | Подключение не разрешает изменение | Не повторять запись; права меняются только новым подключением |
| `NOT_FOUND` | Ресурс отсутствует либо нет доступа | Не раскрывать, какая из причин сработала |
| `BOARD_READ_ONLY` | Разрешённая доска не active | Читать допустимые данные, запись не повторять |
| `ACTION_FORBIDDEN` | Операция запрещена обычной матрицей | Русская безопасная причина, без чужих идентификаторов |
| `INVALID_ARGUMENT` | Некорректные поля | Вернуть имена ошибочных полей без отражения их секретных/личных значений |
| `INVALID_CURSOR` | Неверная граница/другие фильтры | Начать новый поиск |
| `CHECKLIST_CONFIRMATION_REQUIRED` | Есть незавершённые пункты | Спросить пользователя; безопасный count доступной задачи |
| `VERSION_CONFLICT` | Задача изменилась после чтения | Прочитать актуальную задачу, согласовать новое намерение; не перезаписывать автоматически |
| `REQUEST_CONFLICT` | Тот же requestId с другим payload | Не retry; исправить клиентский intent |
| `KEY_ALREADY_ISSUED` | Ключ уже создан, повторный показ невозможен | Только management API: показать metadata и путь отзыва |
| `RATE_LIMITED` | Лимит, HTTP 429 | Подождать `Retry-After`, повторить тот же requestId |
| `TEMPORARY_UNAVAILABLE` | Сервис/БД недоступны | Повторить тот же requestId; timeout сам по себе не доказывает отсутствие commit |

Для отказа из-за чужой доски не возвращать актуальную task DTO, checklist count, имя доски или исполнителя. Сначала authentication/authorization, затем допустимые подробности ошибки.

## 6. Минимальные защитные ограничения

Предлагаемые начальные эксплуатационные границы, не ограничения срока действия ключа:

- Body MCP/management: максимум 64 KiB; списки ограничены пагинацией, поля — schema limits. Отказы до запуска SQL mutation.
- Проверка неверного Bearer: 30 запросов в минуту на реальный peer IP; успешные вызовы — 120 в минуту на connection. Создание подключений — 10 в минуту на пользователя. Ответ 429 содержит `Retry-After`.
- Для первой однопроцессной установки допустим bounded in-memory limiter с TTL и ограничением числа записей. Не доверять IP из клиентского X-Forwarded-For. Перед несколькими экземплярами API лимит переносится на общий ingress/хранилище; не заявлять глобальный лимит при независимых процессах.
- Ограничить длительность DB-транзакции и ожидания lock; не держать connection lock во время внешнего Telegram-запроса. Ошибка лимита/lock timeout не превращается в успешный отзыв.
- Redaction включает Authorization, Cookie, initData, plaintext ключа в management response, request bodies задач. Default logger не должен писать URL с query token до reject; для `/mcp` логировать path без query. Произвольный Error/DB error не логировать с сырым payload.
- Достаточный diagnostic log: request correlation id, tool name, success/error code, duration; connectionId допустим во внутренних access logs, не secret. Тексты задач, состав доски и Telegram identifiers в evidence не включать.
- Текст из БД отображается в UI как текст, не `dangerouslySetInnerHTML`; MCP не исполняет из него shell, SQL, ссылки, встроенные instructions или tools.

Подключение может оставаться активным.»**, действие **«Проверить ещё раз»** повторяет тот же idempotent DELETE, не создаёт новый объект.

### I. Создание: validation, ожидание, неизвестный результат

- Имя слишком длинное: inline **«Не больше 80 символов»**.
- Board access changed: **«Доступ к выбранным доскам изменился. Проверьте выбор.»** Форма не очищается; недоступные доски не подменяются другими.
- Pending: **«Создаём ключ…»**, блокируются повтор и изменения отправляемого payload.
- Явный отказ без commit: безопасная причина над действием, ввод сохранён, можно исправить.
- Timeout: **«Не удалось получить результат» / «Ключ мог быть создан. Сначала проверим подключение, чтобы не создать лишний доступ.»**, primary **«Проверить результат»**.
- `KEY_ALREADY_ISSUED`: **«Ключ создан, но не был получен» / «Показать его повторно невозможно. Отзовите это подключение перед созданием нового.»**, primary **«Отозвать доступ»** с обычным подтверждением. После подтверждённого отзыва — **«Создать новое подключение»**.

### J. Загрузка, offline, нет доступа

- Загрузка списка: skeleton строк и **«Загружаем подключения…»**, без фиктивного пустого состояния.
- Ошибка GET: **«Не удалось загрузить подключения»**, primary **«Повторить»**. Последний известный список не выдаётся за актуальные права.
- Offline: **«Нет соединения. Изменения доступа недоступны.»** Создание/отзыв не помещаются в offline queue; pending outcome остаётся неизвестным до проверки.
- Session expired: **«Войдите снова через Telegram»**. Никаких MCP-ключей для обхода входа. Незасекреченный draft можно держать только в памяти; секрет очищается.
- Потеря всех board grants у подключения: **«Нет доступных досок»**, **«Это подключение больше не даёт доступа к задачам. Его можно отозвать.»** Не создавать новый grant автоматически.

### Responsive и доступность

Для первого review нужны 390×844 и 320×844: форма, выдача секрета и список на обеих ширинах; отдельно 320 для выбора досок, отзыва, clipboard error, потерянного результата и клавиатуры. Вход/пустое состояние/конфигурация — выбранные representative roots. Не размножать весь декартов набор состояний.

- Поля по краям 18 px / 12 px, ширины fluid. Action rows 52–56 px и растут при переносах, touch target минимум 44×44 px.
- Нет горизонтального overflow; URL и secret переносятся без обрезания символов. Не уменьшать UI text ради уместимости.
- С клавиатурой form content прокручивается, submit остаётся достижимым выше клавиатуры с учётом safe area; важное пояснение не скрывается навсегда.
- 200% text scaling, видимый focus, labels, корректный tab order. Sheets удерживают focus, Escape закрывает, focus возвращается в trigger.
- Цвет подтверждается текстом/иконкой. У кнопки отзыва понятное имя, не один красный icon. Clipboard и async states доступны screen reader.
- Статические PNG не доказывают keyboard behavior, focus trap, screen reader, API или Telegram device behavior. Эти gates остаются на реализации и #83.

## 8. Матрица угроз и приёмочных проверок

Матрица задана при подготовке контракта. Фактическое покрытие автоматическими проверками и невыполненные пользовательские/device gates перечислены в [verification](issue-82-verification.md); не считать все строки выполненными только по наличию этой таблицы.

| Угроза/сценарий | Механизм защиты | Проверка |
|---|---|---|
| Чужой/угаданный board/task ID | Grant ∩ membership, uniform NOT_FOUND | Из прямого tools/call нельзя получить task, имя, checklist count или receipt чужой доски |
| Выбран не весь аккаунт | Явная allowlist, без автодобавления | Новая собственная доска не видна прежнему ключу |
| Read-only и скрытый write tool | Проверка mode внутри handler | Подменённый tools/call не пишет, независимо от tools/list |
| Подмена actor | User только из ключа | Поле userId запрещено; audit содержит владельца подключения |
| MCP-ключ используется как cookie/API auth | Раздельные входы | Bearer не создаёт подключение, не читает весь REST API; cookie не даёт MCP доступ |
| CSRF создания/отзыва | Session + exact Origin + JSON | Чужой Origin и запрос без Origin не выполняют management mutation |
| Отзыв/запрос в полёте | Конфликтующие connection locks | После подтверждённого revoke новые writes невозможны; порядок commit доказан гонкой |
| Потеря membership | Grant invalidation + live check | Известный task ID и сохранённый receipt недоступны; rejoin не оживляет grant |
| Архив/заморозка | Общий board status | Разрешённое чтение сохраняется, все writes запрещены |
| Чужой исполнитель/создатель | Общая матрица #73 | Assigned/unassigned done, reopen, обычный member и create done проверены |
| Задача-блокер | Общая валидация и board lock | Чужая доска, self/cycle, done blocker отвергаются; корректное завершение снимает блокер |
| Checklist race | Общая transaction-aware проверка | Не завершает без confirmation; конкурентное изменение не обходит guard |
| Потерянный ответ создания задачи | Durable receipt | Retry с тем же id создаёт одну задачу и один created audit event |
| Повтор update после UI изменения | Receipt до новой mutation, expectedVersion | Старый повтор не перезаписывает свежую задачу; новый stale intent даёт VERSION_CONFLICT |
| Один requestId, другое содержимое | Fingerprint | REQUEST_CONFLICT без частичной записи и побочных эффектов |
| Crash/rollback | Task/audit/receipt в одной транзакции | Нельзя получить задачу без receipt или receipt без задачи |
| Потерянный ответ выдачи ключа | Hash-only + createRequestId | Нет повторного plaintext и второго подключения; UI проводит отзыв потерянного ключа |
| Кража/утечка ключа | Hash-only, no-store, redaction, ручной отзыв | Logs/GET/URL/exports не содержат secret; DB dump не даёт plaintext |
| Перебор/DoS | CSPRNG, schema/body/rate limits | Слишком длинный ключ/body/cursor/query отвергается до дорогой операции |
| Prompt injection в задаче | Текст — данные, нет execution/fetch | Вредоносный description не меняет grants, не исполняет shell/SQL и не вызывает внешнюю сеть |
| Межклиентная утечка | Контекст на запрос | Параллельные разные ключи не обмениваются actor, tool permissions или payload |
| Пагинация | Bounded keyset + повтор прав | Перебор до nextCursor=null без придуманного total; tampered cursor не расширяет доступ |
| Telegram доставка | Существующий intent claim | Повтор не дублирует notification intents, ошибка доставки не отменяет сохранённую задачу |
| UI failure/clipboard/keyboard | Явные состояния и accessibility | Ввод/секрет не теряются при ошибке копирования, focus и primary доступны на 320 |

## 9. Реальный smoke из Hermes — процедура, не выполненный результат

Это исходная процедура полной матрицы, а не утверждение о выполнении каждого пункта в production. Фактически пройденные Hermes-сценарии и отличие от локальной SDK/security-матрицы перечислены в [итоговом отчёте](issue-82-production-smoke.md).

1. По отдельной команде поднять API с изолированной TEST_DATABASE_URL; убедиться, что это не production. Использовать только синтетических пользователей и personal/chat/pair доски. Миграции только в тестовой БД.
2. Сначала выполнить transport smoke через реальный SDK Client: initialize, tools/list, read, write, retry, 401, 405 JSON и disconnect. Проверить Fastify hijack/cleanup и отсутствие контекста между запросами.
3. Для полноценного Hermes gate выбрать разрешённую тестовую учётную запись и действующий способ Telegram-входа. Auth mock годится для автоматических DB/browser tests, но не называется реальным пользовательским подключением.
4. Создать read-only и read-write подключения через UI, прочитать обратно выбранные права. Secret переносит владелец локально в secret scope тестового профиля Hermes. Не запрашивать ключ в чате и не читать существующие credential files.
5. Конфигурация клиента: `mcp_servers.task_kanban.url` — фактический тестовый HTTPS origin + `/mcp`; `headers.Authorization` — `Bearer ${TASK_KANBAN_MCP_KEY}`; `protocol: legacy`; `ssl_verify: true`; `supports_parallel_tool_calls: false`; `tools.resources: false`; `tools.prompts: false`. Поле `auth: oauth` и legacy SSE transport не задаются. User approval policy клиента не ослабляется.
6. Запустить настоящий Hermes, получить инструменты, перечислить разрешённые доски, прочитать задачу. Создать синтетическую задачу, поменять срок/исполнителя/статус в пределах прав. Readback через `get_task` и UI подтверждает DB-состояние и правильного actor.
7. Выполнить negative probes read-only, невыбранной/чужой доски, direct write name, подмены userId. Затем отозвать ключ в UI и из той же Hermes-сессии получить отказ; для другого подключения удалить membership и проверить известный task ID.
8. Потерять ответ после commit и повторить исходный requestId: проверить отсутствие дубля задачи/audit/notification intent. Новый intent со старой expectedVersion должен конфликтовать, не перезаписывать UI.
9. В evidence сохранить версии клиента/SDK, согласованный protocol, команды и реальные результаты проверок, не ключи/задачи/участников. Совместимость иных MCP-клиентов перечислять только при самостоятельном тесте.

Корневые gates после реализации: `npm run test:unit`, `npm run test` с TEST_DATABASE_URL, `npm run lint`, `npm run typecheck`, `npm run build`, `npm run test:visual`. Новый MCP suite должен входить в реальный root gate, не только лежать в папке. Сейчас lint является alias typecheck. Платные GitHub Actions/Packages не включать. Device-only результаты и общий readiness остаются в #83.
